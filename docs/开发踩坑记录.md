# 开发踩坑记录

`CLAUDE.md` 里是结论，这里是案发现场。每条都有当时的实际现象和根因，方便下次
遇到相似症状时对照。按"下次最可能再犯"排序，不按时间。

---

## 一、测试测的不是它以为的东西

这是本项目返工次数最多的一类，六次。共同点：测试给出了一个确定的红或绿，但它
观测的对象根本不对，于是红了查不出原因，绿了也不代表功能正常。

### 1.1 订正规则测不到目标题（m5、m6 各一次）

**现象**：断言"那道错题在两轮专项里都被答对"，期望 2 实际 1。

**根因**：测试挑了错题表里的第一道。专项练习按历史做过次数升序出题，做过的排
在最后；那道题所属考点下有几十道题，40 道的循环根本轮不到它。**测出来的是题库
深度，不是订正规则。**

**改法**：改成挑"所属考点题目最少"的那道错题，并把选中考点的题量打印出来。

```sql
SELECT w.question_id, x.tag_id,
       (SELECT COUNT(*) FROM questions q2
          JOIN question_knowledge_points x2 ON x2.question_id = q2.question_id
         WHERE x2.tag_id = x.tag_id AND q2.status = '已发布') AS n
  FROM wrong_items w
  JOIN question_knowledge_points x ON x.question_id = w.question_id
 WHERE w.corrected = 0
 ORDER BY n ASC LIMIT 1;
```

### 1.2 权重断言选错观测对象（m4）

**现象**：验证"薄弱考点权重高、出题多"，但无论权重调多高都只命中一两次。

**根因**：按 tag_id 排序取第一个考点当"薄弱"，取到的考点总共只有一两道题。抽到
考点后还要从它下面挑没做过的题，题不够就抽不出、退回换别的考点。同样是在测题库
深度。

**改法**：取题量最多的考点，并把考点名、题量、已出过的题数一并打印。

### 1.3 阈值和理论值对不上（m4）

阈值写 ≥3，而按权重算出来的期望值是 2.8。断言本身就不可能稳定通过。

### 1.4 断言了算法并不保证的性质（m4）

**现象**：断言"摸底阶段考点不重复"，偶发失败。

**根因**：一道题可以同时挂两个考点。为新考点出的那道题顺带覆盖了已见过的考点，
完全正常。算法真正保证的是"每道题都带来至少一个新考点"。

**教训**：断言之前先想清楚算法承诺的是什么，不要把自己的想当然写成断言。

### 1.5 写死的期望值过期（m2）

**现象**：全套回归时 m2 四条断言同时红——"发布50题"实际 39、"存疑题保留未发布 1"
实际 12、"已发布题数为50"实际 39、"非存疑题全部已发布 101"实际 89。

**根因**："存疑记录点名的题不参与组卷"这个改动落地后，各类计数全变了，而这些
数字是写死在测试里的。

**改法**：开跑前从库里数出总题数和存疑数，期望值现算。

### 1.6 循环断言（m2）

**现象**：断言"非存疑题全部已发布"长期是绿的。

**根因**：它拿库里的已发布数去对接口返回的已发布数，两边同源，永远相等。**漏发
根本测不出来。**

**改法**：期望值按"非存疑"计数，和被测对象不同源。

## 二、本地替身照不出的问题

`worker/test/ai-stub.mjs` 按我们要的形状瞬间返回。这让它对降级路径和协议约束很
有用，但下面两类问题它结构上就测不出来。两个都是靠 `prod-e2e` 流水线在真实服务
商上打出来的。

### 2.1 串行调用导致请求超时

**现象**：线上实测 `POST /api/ai/attempts/:id/run` 60 秒无任何返回；但同时错题
本里已经有 13 条带上了 AI 错因——**服务端一直在干活，只是客户端等不到。**

**根因**：接口先批改作文，再逐条分析错题，全串行。Qwen3-8B 一次调用 3-4 秒，
错题最多 20 条，整个请求 80 秒以上。替身瞬间返回，串行毫无问题。

**改法**：`lib/ai.js` 加 `mapLimit`，并发上限 5。20 条分四批约 15 秒，实测整段
从超时变成 30 秒。上限取 5 是为了压总时长的同时不打爆供应商速率限制。

### 2.2 返回结构不符导致静默 0 分

**现象**：作文状态"批改成功"，分数 0，而那段作文是通顺的英文。

**根因**：取维度分只认顶层的 `content`/`language`/... 五个数字键，`Number()` 取
不到就一律回落 0。真实模型返回的 JSON 合法但键名不是这套，五个维度全落空，合成
出 0 分，状态还标成功。

**改法**：顶层没有就往 `scores`/`score`/`result`/`dimensions` 找，`"5.5分"` 这类
字符串也认；**一个维度都读不到就抛 `ai_bad_shape`**，错误信息带上实际看到的顶层
键名。真的 0 分和读不到 0 分必须分得开。见 `worker/test/essay-parse.mjs`。

## 三、D1 免费额度耗尽导致整站不可用

**现象**：登录返回 HTTP 500，后改为 503 `storage_quota_exceeded`。

**根因链**（花了很久才理清）：

1. 流水线每次部署无条件重导整套题库，一次约 5700 行写入。
2. 免费版每天 10 万行，连着部署十几次就到顶。
3. 到顶后所有写操作失败——包括登录时更新最后登录时间，于是登录也 500。

诊断本身被挡了两次：第一次流水线日志尾部被 `request.cf` 的输出占满；第二次
GitHub Actions 回显了 45 行内联 shell，把日志尾部撑爆。**把 shell 挪进
`scripts/ci/*.sh` 之后才看到真正的错误。**

### 3.1 指纹和数据不同批，导致死循环

修了无条件重导之后又踩一个更隐蔽的：种子导入分两步——先 `d1 execute --file` 导
数据，再单发一条 `INSERT` 记内容指纹。第一步成功、第二步撞额度失败，结果**数据
进去了、指纹没记上**；下一次部署认为文件没导过，原样重导，再死在同一处。每跑一
次白烧约 578 行，永远走不出来。

**改法**：由 `build-seed-sql.mjs` 把 `seed_state` 的 upsert 写成种子文件的最后
一条语句。`d1 execute --file` 是一次导入，数据和指纹同生共死。

### 3.2 数据装载挡住了代码发布

题库导入排在部署前面，导入一失败后面的部署整步跳过。**连续八次运行，M4 到 M6 的
Worker 代码一行都没上线。** 顺序改成：迁移 → 部署 → 写密钥 → 导题库。迁移仍排
最前，因为新代码可能依赖新表；迁移都是 IF NOT EXISTS，稳态零写入。

### 3.3 修完降级之后，哨兵没了

登录改成"额度用尽也放行"之后，线上验证的十几条断言全是读类，**额度耗尽时读接口
全都正常**，于是流水线全绿也说明不了站点能用。补了一条：读 AI 配置的
`updated_at`，看离现在多久——AI 配置每次部署都重写，额度用尽时会回退成沿用旧值，
时间戳就会停在上一次成功部署。

## 四、本地跑测试的环境坑

### 4.1 workerd 子进程活过了清理

只杀 wrangler 本身杀不掉 workerd，它继续占端口，下一轮报 Address already in use，
同时一直提示一个已被删掉的构建临时路径——很容易把注意力引到构建上去。用 `setsid`
让服务自成进程组，退出时整组一起杀。

### 4.2 `pgrep -f` 杀掉自己

`pgrep -f wrangler` / `pkill -f` 的模式会匹配到发出这条命令的 shell 本身，反复
把自己杀掉（退出码 144）。改用
`ps -eo pid,args | awk '/wrangler[ ]dev/ {print $1}'`，方括号让模式匹配不到自己。

### 4.3 就绪等待不够长，且不报错

`wrangler dev` 启动时要连几个被出站策略拒绝的 cloudflare.com 地址，要重试到超时，
启动一分多钟。原来的就绪等待只有 30 秒，等不到也不报错，直接拿一个没起来的服务
跑完整轮，产出一堆互不相关的失败。改成最多等 150 秒，等不到就打印 dev 日志尾部
后退出。

### 4.4 新测试和老测试撞端口

新加的 `ui-smoke.sh` 用了 8794，和 `m5-smoke.sh` 一样。加新套件前先看 `CLAUDE.md`
里的端口表。

### 4.5 失败被 `2>&1` 吞掉

m2 只跑到 0004 号迁移，而 `seed_state` 建在 0006，加了新语句后种子导入必然失败
——但那行是 `>/dev/null 2>&1` 且没判返回值，测试静默退出，**连小结都不打**。所以
跑全套时那句 `|| echo "!! 没有小结"` 很重要。

### 4.6 边执行边编辑脚本

bash 正在执行某个脚本时去改它，会在毫不相干的行报语法错误。

## 五、改代码本身的坑

### 5.1 锚点只匹配了半行

给 `export const studyRouter = new Hono();` 前面插入一段常量定义，锚点用的是
`const studyRouter = new Hono();`，结果变成：

```js
export // 注释
const WRONG_ANALYZE_CONCURRENCY = 5;

const studyRouter = new Hono();
```

`export` 跑去修饰常量，`studyRouter` 不再导出，构建报
`No matching export in "src/routes/study.js" for import "studyRouter"`。

五套回归里 m5、m6 连小结都打不出来，就是这个原因。**锚点从行首取到行尾**，
并且语法检查过了还得真跑一遍——`node --check` 查不出这种问题。

### 5.2 `set -e` 下的 `[ ... ] && cmd`

条件为假时整个步骤退出。改写成 `if`。

### 5.3 `UID` 是 bash 只读内建变量

赋值会报错。测试里改名成 `USER_ID`。

## 六、GitHub Actions 的坑

### 6.1 只手动触发的流水线注册不了

`workflow_dispatch` 单独存在时，非默认分支上的新流水线 GitHub 不认得（dispatch
返回 404），而没跑过就不会被认得——死结。给一个 `paths` 限定到它自己文件的
`push` 触发来破局：改测试本身时跑一次正好，平时不触发。

### 6.2 日志尾部被撑爆

大段内联 shell 会被 Actions 完整回显，把日志尾部占满，真正的报错被挤出可见范围。
超过几行的逻辑放进 `scripts/ci/*.sh`。

### 6.3 admin 被登录限流锁住

连续 5 次失败会锁 10 分钟。流水线在登录前会先清一次 `login_attempts`；另外
`ADMIN_PASSWORD` 和 `ADMIN_PASS` 两个 Secret 名字都认，但每个只试一次，不重试，
免得把 5 次的额度烧光。

### 6.4 部署后立刻验证，打到的是旧代码

`wrangler deploy` 完成后 6 秒就去登录，命中的还是旧版 Worker。重跑一次就过了。
判断"新代码是否生效"要用能区分新旧行为的信号，不要只看部署步骤成功。

## 七、外部工具不可用

- **LibreOffice 起不来**：连最小 docx 都报 `source file could not be loaded`，
  换 ASCII 文件名、换 `-env:UserInstallation`、换 txt 源文件都不行，连 txt 都转
  不了，是整体不可用。生成 Word 后没法转 PDF 看版式，只能做 schema 校验
  (`validate.py`，需要先 `pip install defusedxml lxml`) 加读回 `document.xml`
  正文核对，**版式要如实说明没亲眼确认过**。
- **`pandoc` 没装**，读 docx 得自己解 zip 解析 XML。
- **Playwright 装在哪要看清楚**：`cd A && npm i` 之后再接一条 `cd B` 的复合命令，
  第二条的 `cd` 不会生效，包会装错地方。装完确认 `ls -d <pkg>/node_modules/xxx`。
- Playwright 进了 `worker` 的 devDependencies 后，CI 的 `npm install` 会触发它下
  载浏览器，要加 `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`。不能改用 `--omit=dev`，
  因为 `wrangler` 也在 devDependencies 里。

## 八、写测试和文档时的取材原则

- **浏览器测试的选择器要锚在页面自己的内容上。** 用 `text=模拟考试` 等待首页
  加载会命中导航栏里的同名链接，而手机上导航是收起来的，永远等不到——那测的是
  导航不是首页。改用 `text=可用真题` 这种只出现在页面主体的字。
- **浏览器测试必须可重复跑。** 早期版本挑"数据库里现成的未批改卷子"，跑第二遍
  时现成的已经被上一遍批改掉了。改成测试自己造一份。
- **写文档前先把界面实际文案抓出来**，不要照着需求文档编。这次写学员手册时就
  因此发现登录页副标题两处错：把 00015 写成"英语（一）"（实为英语二），而且课程
  早已合并成一门却还在列两个。

## 九、改造成多学科平台时新踩的（N0～N2）

### 9.1 `database_id` 跟着复制过来，差点写坏老站的线上库

本平台是从 Eng1300 复制的，`wrangler.toml` 的 `database_id` 原样带了过来。没清掉
的话，本平台的迁移会直接建在 Eng1300 的线上库上。而迁移全是 `IF NOT EXISTS`——
**不报任何错、流水线全绿、老站数据被静默改坏**。

守卫 `scripts/ci/check-db-isolation.sh` 挂在所有 d1 操作之前，禁用名单在
`scripts/ci/forbidden-databases.txt`，守卫自己有单测 `worker/test/db-isolation.sh`。
写完守卫先证伪了一遍：改成恒放行时 7 条拦截断言变红，恒拒绝时 3 条放行断言变红。

### 9.2 改库名，六个测试脚本当场失效

N0 把库名和 Worker 名从 `eng1300-mvp` 改成 `xlearn`，六个脚本里写死的库名全废。
wrangler 报的是"找不到该数据库"，看起来像环境问题，不像改名漏改。现在一律从
`wrangler.toml` 读。

### 9.3 中间件里 `c.req.param('id')` 永远是 undefined

N2 的 `requireAttemptAccess` 用 `use('/attempts/*')` 按前缀挂。`c.req.param('id')`
只对模式里真有 `:id` 的 handler 有效，前缀挂的中间件自己的模式里没有，取到的永远
是 undefined。代码写的是"取不到 id 就 `next()`"，于是**该 403 的地方返回 200，
从外面看一切正常**。

是被那条"撤销立即生效，取卷被拒"的断言逮住的。根因不是 Hono 的怪癖，是我写了个
"取不到值就放行"的回落——正好撞上标准里"读不到值就抛错，不要回落默认值"。现在从
`c.req.path` 自己解析。

**推论：每种路径形状都要单独断一条。** `/attempts/:id`、`/attempts/:id/report`、
`/practice/:id/next`、`/ai/attempts/:id/run` 走的是不同的匹配，只测一个过了不代表
其余的也过。

### 9.4 迁移里的补授权，会把管理员撤销过的授权插回去

流水线每次部署都把 `migrations/*.sql` 全部重跑。N2 那段"给既有学员补授权"是
`INSERT OR IGNORE`，不加门闩的话，管理员撤销过的授权会在下次部署被默默插回来
——不报错、日志里看不出来。门闩记在 `seed_state`，与被门闩的操作同属一次
`d1 execute --file`。

### 9.5 权限层差点只是个装饰

N1 把接口搬迁推迟到了 N7，所以老接口还在老路径上。只在 `/api/s/*` 挂中间件的话，
被撤销的学员照样能从 `/api/exams/generate` 组卷。按三类分别处理：收 courseCode 的
和带 attempt id 的返回 403，跨学科聚合的只能**过滤行**。

过滤类最容易漏，因为它不能整个 403，漏了不报错，表现为"学科撤了，历史记录里那几次
模考还在"。

### 9.6 新加的权限把六套既有测试全弄红了

N2 之后新建学员默认没有任何授权，而六套脚本都是"建学员 → 直接做题"。这是改对了
以后的必然后果，不是 bug，但要记住：**加一条默认更严的约束时，先去数有多少地方
依赖旧的宽松默认**。

### 9.7 断言恒真：学科没授权，本来就不出现在列表里

`n1-subjects.sh` 里"停用后不出现在列表里"这条，在 N2 加了授权之后变成恒真——那个
学科本来就因为没授权而不出现，测不出停用有没有生效。补了一条"停用前确实出现"在
前面顶着。

同理，"学员看到全部启用中的学科"的期望值也得从"所有启用中的"改成"已授权 ∩ 启用"。

### 9.8 只断 HTTP 码不够

"改学科码被拒"只断 400 的话，把 `IMMUTABLE` 清空后返回的是 `nothing_to_update`，
也是 400，照样绿。真正逮住它的是旁边那条断错误码的。

### 9.9 N1 改了路由，而我没跑浏览器测试

`ui-smoke.sh` 走 `/app/exam/new`，N1 之后 `exam` 会被当成学科码解析。它在 N1 那轮
回归里根本没被跑到——回归清单漏了浏览器这两套。全套的定义要包含它们。

### 9.10 改建表语句对已经存在的库毫无作用

N3 把 `questions` 的题型 CHECK 去掉、`knowledge_points` 加学科维度，改的是
`0002_bank.sql`。迁移全是 `CREATE TABLE IF NOT EXISTS`，对已有表一行都不改——
新库照着改好的语句一次建对，线上那个 N0 时期建的库还是旧结构。**本地测试每次都是
新库，全绿；线上不变，也不报错。**

补救是一道按实际结构判断的重建脚本，并且要**排在迁移之前**：0002 里新加的
`idx_questions_subject` 建在 `subject_id` 上，旧表没这一列，迁移会整条断在那句。
这件事是写 `n3-rebuild.sh` 时被测出来的，不是想出来的。

### 9.11 D1 不让 DROP 有子表引用的父表

`PRAGMA defer_foreign_keys` 与 `legacy_alter_table` 在 D1 里都不生效，报
"Durable Object was reset and rolled back ... FOREIGN KEY constraint failed"。
试过 `ALTER TABLE 改名 → 建新表 → 搬数据 → 删旧表`，结果是**半完成状态**：新表建好了、
旧表没删掉、子表外键跟着改名指向了旧表。这比直接失败更糟，因为查询还能跑。

SQLite 又改不了 CHECK 和主键，所以最后的做法是先清空引用它的行（题库与作答记录都是
可重新生成的），再拆表让迁移重建。

### 9.12 改主键会连带打断 upsert，而且是静默的

`ai_settings` 主键从 `purpose` 改成 `(purpose, subject_id)` 之后，`admin-ai.js` 里
那句 `ON CONFLICT(purpose) DO UPDATE` 不再匹配，写入静默失效——接口返回 200，
读回来是 null。是 m2-smoke 的四条 AI 配置断言逮住的。改主键时要把所有
`ON CONFLICT` 一起找出来。

### 9.13 "行为跟着配置变"才是配置化的证据

把写死的规则搬进数据之后，只断言"英语判分还是对的"证明不了任何事——写死的代码同样
能让它通过。每条都要配一对：默认配置下是 A，改掉配置之后变成 B。比如摘掉
`en-spelling` 之后 `travelled` 必须判错，装回去又判对。变不动的那条，说明规则还留在
代码里，声明只是摆设。

### 9.14 提示词进了数据库，替身却还按提示词文本分发

N3 把四类 AI 提示词搬进 `subject_ai_prompts`，模板措辞跟着变了一点
（`批改这篇自考英语作文` → `批改这篇{{subjectName}}作文`）。
而 `test/ai-stub.mjs` 是**按提示词里的固定短语**决定返回什么的，匹配不上就回落成
`{ ok: true }`——于是 AI 调用"成功"、作文却判不出分，报出来只有一句 `ai_bad_shape`。

两个结论：

1. 提示词现在按学科各存一份，**英语那份要与蓝本逐字一致**。改措辞就是改真实模型的
   输出分布，等于悄悄改了判分，而不会有任何断言变红。通用化不等于把每个学科专属的
   字眼都换成占位符——能力包本来就允许各学科措辞不同。
2. 替身分发不到时要**明说**，不要回落成一个看起来合法的对象。现在它返回
   `{ stubCannotClassify, hint, promptHead }`，错误信息里直接就能看出根因。

### 9.15 跨 handler 用了另一个 handler 的局部变量

给 `/assessment` 加了 `const assessPack = ...`，却在 `/ai/assessment` 里用它——
两个不同的 handler，运行时是 ReferenceError。`node --check` 查不出这种错（它不是
语法问题），m5 里表现为"AI 定性评估返回水平定位"变红。

再一次印证：**静态检查通过之后必须真跑一次**。同一个文件里有多个 handler 时，
加变量前先确认自己在哪个函数体里。

## 十、事故：线上题库被清空（2026-09-23，部署 #44）

### 10.1 经过

N3 的旧库重建脚本（`scripts/ci/rebuild-legacy-schema.sh`）按「建表语句里有没有旧约束」
判断一张表是新结构还是旧结构。我在改 `0002_bank.sql` 时，把那条被去掉的旧约束原文
抄进了紧挨着的注释里：

```sql
-- 原来是 CHECK (question_type IN ('single_choice','fill_blank_transform','essay'))，
```

而脚本的特征串正是 `CHECK (question_type IN`。**线上 D1 的 `sqlite_master.sql` 保留
注释**，于是新表每次都被当成旧表，每次部署都把 `questions` 连同作答记录清一遍。

#43 没暴露，是因为那一轮种子内容指纹变了、题库会重新导入，正好把坑填上；
#44 指纹没变、导入跳过，题库就空在那儿了——20 套试卷还在、1020 道题没了。

### 10.2 为什么本地测不出来

**本地 workerd 会把建表语句里的注释剥成空行，线上 D1 不会。**
所以 `n3-rebuild.sh` 那 28 条断言（包括"再跑一次必须是空操作"）在本地全绿，
它查的是 `sqlite_master`，而本地的 `sqlite_master` 里根本没有那行注释。

这是替身盲区的又一种形态：不是"替身返回的形状不对"，是**同一个存储引擎的本地实现
与线上实现在某个细节上不一致**，而恰好这个细节决定了判断结果。

### 10.3 三个错叠在一起

| # | 错 | 对应的规则 |
|---|---|---|
| 1 | 锚点取了会出现在更大结构里的片段（注释） | §5.1「锚点只匹配了半行」，CLAUDE.md 也明写了 |
| 2 | 本地与线上行为不一致，而测试只在本地跑 | §2「替身的盲区」 |
| 3 | **会删数据的动作按每次重新判断，没上门闩** | §9.4「只该跑一次的迁移要有门闩」 |

第 3 条才是根本。前两条是"这次判断错了"，第 3 条决定了"判断错一次会有多严重"。
我在 N2 给迁移上过门闩，却没想到给这个脚本上——因为它长得像一段检查，
不像一次迁移。**判据不是它长什么样，是它会不会删数据。**

### 10.4 还缺一条不变量

拆掉题库之后没有让种子的内容指纹失效。有这条的话，误判的后果只是每次部署多导一次
题库（浪费额度，会被 `rows_written` 看出来），而不是留下一个空题库，还一路绿到
验证步骤才被两条断言拦住。

**凡是"删掉由某个指纹守护的数据"，就必须在同一步里把那个指纹也删掉。**

### 10.5 现在的防线

1. 门闩记在 `seed_state`（`n3-legacy-rebuild`），做过就再也不判断；
2. 比对前先剥 SQL 注释；
3. 拆题库的同时作废题库种子指纹；
4. `n3-rebuild.sh` 加了一条**环境无关**的回归：直接拿脚本里的特征串去比对
   `0002_bank.sql` 的原文（含注释），不查 `sqlite_master`——本地剥不剥注释都测得出。
   证伪过：把事故那行注释放回去，这条当场变红并点名是哪个串、在哪个文件。

线上验证的两条断言（"题库已导入 1020 道题"、"英语学科已有可抽题"）是这次唯一拦住
事故的东西。**它们值这个钱**：在它们之前的所有步骤都是绿的。

## 十一、部署 #48 红在迁移：旧库上"提到新列"就够了

### 11.1 经过

N5 给 `subject_question_types` 加了 `answer_shape` 与 `grading_strategy` 两列。
做法是老规矩：新库从 `0009` 的建表语句里带着这两列，旧库靠
`scripts/ci/ensure-columns.sh` 补列加回填——那个脚本就是为这件事写的，
N5-1 时已经验过它在"列缺失"的库上能补上并回读确认。

推上去之后流水线红在 **Apply database migrations**：

```
✘ [ERROR] table subject_question_types has no column named answer_shape: SQLITE_ERROR
```

后面所有步骤（补列、部署、导题库、线上验证）全部跳过。**线上因此什么都没变**，
老代码继续在跑，没有用户影响——但也说明这次是运气好：失败发生在部署之前。

### 11.2 根因

我给 `0009` 的七条题型种子补了列清单：

```sql
INSERT OR IGNORE INTO subject_question_types
  (..., sort_order, answer_shape, grading_strategy)
SELECT ..., 'CHOICE_ONE', 'EXACT'
  WHERE NOT EXISTS (SELECT 1 FROM seed_state WHERE name = 'n3-pack-seed');
```

那个 `WHERE NOT EXISTS` 是 N3 的门闩，线上早就合上了，**这条语句一行都不会插**。
但它照样把整个迁移步骤弄红了，因为 **SQLite 在准备语句的时候就校验列名，
根本走不到 `WHERE`**。

于是顺序错了：补列脚本排在迁移**之后**，而迁移本身需要那两列已经存在。

### 11.3 为什么本地测不出来

本地测试每次 `rm -rf .wrangler` 重建库，新库从建表语句里就带着这两列，
"旧库 + 新迁移"这个组合在本地根本不存在。这和第十节是同一类问题的不同形态：
**本地与线上的差别不在行为上，在"库是从哪一步开始的"上。**

### 11.4 现在的防线

1. 补列步骤移到迁移**之前**。新库走到那一步时表还没建，整步是空操作，
   由迁移把表连列一起建好；旧库则是先补列再迁移，迁移里提到新列也没问题。
2. `n5-items.sh` 加了一段**旧库模拟**：先 `ALTER TABLE ... DROP COLUMN` 把两列删掉
   （本地 D1 支持），然后
   - 反面：直接跑 `0009`，断言它**失败**且报错点名 `answer_shape`；
   - 正面：按流水线的顺序先补列再跑全部迁移，断言都过、且旧行的策略被回填。
   反面那条不能省：没有它，正面那条说明不了"顺序"有没有用。

### 11.5 教训

**"这条语句不会执行"不等于"这条语句不会出错"。** 门闩管的是要不要写，
列名校验发生在那之前。凡是在迁移里提到"这次新加的列"，都要先确认那一列在
**最老的那个库**上已经存在。

## 十二、约束改不动的两处，和它们逼出来的形状（N6，2026-09-24）

需求文档 §6.4.2 要 `exams.year/month` 放宽为可空，§6.4.10 要 `questions.status`
从三值扩到五值（加 `缺答案`、`待核`）。**两条都做不到**，而且做不到的原因是同一个。

### 症状

SQLite 的 `ALTER TABLE` 只有 RENAME / ADD COLUMN / DROP COLUMN 四种，
**改不了 `CHECK`，也去不掉 `NOT NULL`**。要改就得重建表。
而 `exams` 有 `sections`、`questions` 两张子表引用，`questions` 有五张，
D1 又不让 DROP 有子表引用的父表（`PRAGMA defer_foreign_keys` 与
`legacy_alter_table` 都不生效，报的是 "Durable Object was reset and rolled back"，
见第十节）。重建的唯一走法是先清空引用它的行——那就是清空题库和作答记录。

**为了给状态多一格而清一次题库，代价和收益不成比例。**

### 做法

| 文档要的 | 实际落成 | 代价 |
|---|---|---|
| `status` 加 `缺答案` / `待核` | 单开一列 `answer_state` | 状态分成两个维度，查询要带两个条件 |
| `year/month` 放宽为可空 | 保持 NOT NULL，没有年月的学科写 0 | 0 是个假值，必须保证它出不了库 |

两处各配一条不变量，**不变量不成立时这两个决定都是错的**：

① **`answer_state` 不加 `CHECK`。** 这一列存在的理由就是上一条 CHECK 加不进去
也去不掉，再种一个一模一样的雷没有道理。合法取值放在
`worker/src/lib/pickable.js`，三个入口（种子生成、导入器、后台接口）各校验一次。

② **抽题判据只有一处。** 判据从"`status = '已发布'`"变成两个分量之后，
散落在七处查询里（组卷三处、练习三处、题型清单一处）。漏掉一处的症状是
"某道缺答案的题偶尔出现在练习里"——抽题带随机，测不稳，线上要很久才被撞见。
所以写成 `pickableSql(alias)`，七处都引它。

③ **判据写严不写松。** `answer_state = '已确认'`，不是
`IS NULL OR = '已确认'`。漏填一行时，严格比对的表现是"符合条件的已发布题只有
N 道"（吵），放过 NULL 的表现是把一个没人核过的答案发给学员（静）。
这一条要的就是吵。线上老库补出来的列在回填前确实是 NULL，那由
`ensure-columns.sh` 的回填后检查兜——回填不全就让部署当场失败，新代码不上线。

④ **0 只存在于 `exams` 表里。** 读出去的那一刻映射回 `null`，映射只在
`worker/src/lib/content-group.js` 的 `shapeContentGroup` 一个函数里做，
界面一律显示 `label`。这样"哪里会漏"有一个确定的答案，而不是每加一个页面
就要重新想一遍。反例就在手边：`BankList.jsx` 原来写的是
`{e.year} 年 {e.month} 月`，生化的章节会显示成"0 年 0 月"。

### 顺带暴露的越权

`/api/courses` 是蓝本留下的、唯一一个不带学科过滤的列表接口。蓝本只有一个学科，
所以不过滤看不出问题；生化的课程行一进库，**只授权了英语的学员在这个接口上
就能看到生化**。这不是"多显示一行"，是 N2 那一类越权。
加课程行的那次 `m2-smoke` 从 40/0 变成 40/1，才把它翻出来——
**"加一行数据导致一条断言变红"值得先看懂再改期望值。**

### 附一：D1 的 compound SELECT 分支数卡得很低

`ensure-columns.sh` 的列清单从 5 个涨到 17 个之后，逐列查"这列有几行是空的"
要十几次 `npx wrangler d1 execute`，每次都要起一个 node 进程——本地这一步从几十秒
涨到三分钟，线上每次部署也要多花好几分钟。

想当然的做法是拼成一条 `UNION ALL` 一次查回来。**D1 不让**：实测 5 个分支能过，
10 个报 `too many terms in compound SELECT: SQLITE_ERROR`（标准 SQLite 的默认上限
是 500，D1 的 workerd 显然另有一套）。更麻烦的是**它报的是一个错误对象，不是非零
退出码**——`jq` 取不到 `.results` 就静静返回空，症状是"每一列都读不到空值行数"，
看起来像缓存写坏了，跟 SQL 一点关系都没有。

改成**一张表一条 SELECT、每个目标列一个 `SUM(CASE WHEN … IS NULL …)`**，
就没有分支数这回事了：17 次调用变成 5 次，整步 3 分钟变 31 秒。
两个附带的坑：空表上 `SUM` 返回 `NULL` 不是 `0`（要套 `COALESCE`），
以及**关联数组的缓存写在 `$( )` 里是白写的**——命令替换是子 shell，
它读得到父 shell 的变量，但写回不去，于是"缓存"每次调用都重新查一遍。
预热要放在主 shell 里。

### 附二：跑回归的时候别动 worker/public

这一轮 `m4-smoke` 在 21 条之后成片报 `实际 000`（服务没了），单独重跑 37/0。
原因不在被测代码：我在批次跑着的时候在另一个窗口跑了 `npx vite build`。
`vite.config.js` 的 `emptyOutDir` 会先清空 `worker/public`，而 `wrangler.toml` 的
`[assets]` 指着它——正在跑的那个 `wrangler dev` 当场重载，重载时打断了正在进行的请求。

CLAUDE.md 早就写了"不要在 bash 正在执行某个脚本时去编辑它"，但当时说的是编辑脚本本身。
**构建前端也算**：它改的是被测服务正在用的文件。回归跑起来之后，只改 `docs/`。

### 由此定下

- 加状态、放宽约束之前，先查这张表在不在别人的外键上。在，就当它改不动，
  从"加一列 + 一处判据"开始想，而不是从"改 CHECK"开始想。
- 用假值占住 NOT NULL 时，**先定死它的唯一出口**，再写第一处写入。
- 断言的期望值是从数据算出来的还是抄下来的，要分清楚。
  `Object.keys(NORMALIZERS).sort().join(',')` 对一串写死的名字，
  测的是"有没有人加过归一化器"，每加一个能力就红一次，而红了之后正确的做法
  永远是改期望值——这种断言不提供任何信号，改成断言它要守的那条性质
  （名字里不许出现学科名）。

## 十三、workerd 强制外键，而种子的"先删后插"删不动被作答过的题（N6b，2026-09-24）

写 N6b-2 的正面对照断言时撞出来的，**不是那条断言的问题，是一个隐患**。

### 症状

一套英语真题，学生（或测试）组过卷之后再重新导入它的种子文件，报：

```
✘ [ERROR] FOREIGN KEY constraint failed: SQLITE_CONSTRAINT (extended: SQLITE_CONSTRAINT_FOREIGNKEY)
```

**一句光秃秃的外键失败，不说是哪张表、哪一行。** 在流水线里它会表现为"导题库那一步红了"，
而种子文件本身一个字没错。

### 根因

种子的幂等清理段删的是 `question_knowledge_points / question_assets /
question_items / questions / sections / exam_parsing_notes / exams`，
**没有删引用这些题的作答侧的行**：`attempt_questions`、`answer_records`、
`wrong_items`、`user_knowledge_mastery`。

而 workerd 是强制外键的。CLAUDE.md 里那句"外键在 D1 上默认不强制"说的是
**插入孤儿行不报错**（种子里 `question_assets` 指向已删题目那种），
与"删父行会被子表拦住"是两回事——两句都对，但混在一起读会得出错误结论。
第十节里"D1 不让 DROP 有子表引用的父表"说的其实就是同一件事的另一面。

### 影响面

**题库内容一改就要重导，而学生只要做过那套卷子就删不动。**
现在还没暴露，是因为线上那 20 套的重导都发生在没有作答引用的时候
（部署 #52 全量重导成功）。真学员用起来之后，任何一次题面订正都会撞上。

还有一层不确定：**本地 workerd 强制外键，远端 D1 是不是同样强制，没有验过**。
部署 #52 成功只能说明"当时没有引用行或者没强制"，两者分不开。

### 不要这样修

- ❌ 连作答记录一起删。那是学生的数据，为了改一个错别字抹掉它，不成比例。
- ❌ 关掉外键。它正在拦的是真问题。

### 该怎么修（待排期）

改成**按题 upsert**而不是整卷先删后插：题面变了就 `UPDATE`，新增的 `INSERT`，
删掉的题单独处理（多半该标废弃而不是物理删除）。作答记录指向的 question_id 不变，
就不会撞外键，学生的历史也留得住。

在那之前至少要让失败**说人话**：导题库那一步失败时，把"这套卷子有 N 条作答引用，
所以删不动"打出来，而不是让人对着一句 FOREIGN KEY 猜。

## 十四、测试助手静默失灵，伪装成页面的 bug（N6b，2026-09-24）

### 症状

`ui-n6b.sh` 三种宽度都红在同一条：

```
FAIL 手机｜填完之后"试解析"能点了｜还差：选一个文件（期望 false, 实际 true）
```

学科、内容组 id、显示名、排序依据都填好了，页面的"还差："只剩「选一个文件」——
而测试上一行明明刚 `page.setInputFiles('#imp-file', DOCX)` 过，那一句没抛任何错。

于是第一反应是页面的问题：React 没收到 change 事件？按钮的禁用条件写反了？
构建产物是旧的？我照这三个方向查了一个小时，全部排除：
`worker/public` 里的 bundle 比源码新、`onChange` 原样在、`imp-file` 全页只有一个。

### 根因

**Playwright 1.49.1 的 `setInputFiles` 传一个含非 ASCII 字符的路径时，
一个文件都不会塞进去，而且不报错。** 在一张空白页上隔离测一遍就分得很干净：

| 传进去的东西 | `input.files.length` |
|---|---|
| 中文名路径，无 `accept` | **0**，不抛错 |
| 中文名路径，`accept=".docx"` | **0**，不抛错 |
| 同一份字节，复制成 ASCII 名的路径 | 1 |
| `{name:'第01章…docx', mimeType, buffer}` | 1 |

题库原件全是中文名（`第01章-蛋白质的化学.docx`），所以每一轮都踩。
页面从头到尾是对的：input 里确实没有文件，它说「还差：选一个文件」完全正确。

### 教训

这是标准 §2.1 那条"替身的结构性盲区"的另一个面：
**不只外部依赖的替身会静默失灵，测试框架本身的操作助手也会。**
判据一样——**这次失败会不会被伪装成别的东西**。
`setInputFiles` 不抛错，于是"我没把文件放进去"被伪装成"页面不接受文件"，
而红的那条断言指向的是完全无辜的代码。

所以：**凡是"让页面进入某个状态"的测试助手，都要紧跟一条断言证明它真的做到了**，
再去断被测的行为。这一条只值一行，省下的是对着无辜代码查一小时。

```js
await page.setInputFiles('#imp-file', { name: DOCX_NAME, mimeType: DOCX_MIME, buffer: DOCX_BYTES });
check(`${label}｜文件真的进了 input`, await page.evaluate(() => {
  const f = document.querySelector('#imp-file').files;
  return f.length === 1 ? f[0].name : `files=${f.length}`;   // 0 的时候要说得出是 0
}), DOCX_NAME);
```

### 顺带

改成 buffer 形式不是绕开问题，是把覆盖面变大了：文件名仍然是中文，
走的是页面真正会遇到的那条路（`File.name` → 查询串百分号编码 → 服务端解码 →
`content_group_sources.filename`）。`ui-n6b.sh` 因此多了一条回库断言，
核这条链上没有哪一段把中文名编坏——上传本身编坏了也照样成功，界面上看不出来。

## 十五、中间件查的是一个值，接口用的是另一个值（CR-H1，2026-09-27）

代码审查时读出来、本地复现过的授权绕过，**线上没有被利用的迹象，但从外面看不出任何异常**。

### 症状

只授权了生化的学员，发一个网址和请求体各写一门课的请求：

```
POST /api/exams/generate?courseCode=biochem-main    （网址：有授权的生化）
{"courseCode":"13000"}                              （请求体：没授权的英语）
→ HTTP 201，库里多了一条这个学员的英语考试
```

组卷、开练习两个接口真的建出了英语会话；专项练习、AI 评估也越过了授权检查。
题目内容没漏——取卷、取题走的是按会话查归属的另一道检查，它没被绕过。

### 根因

授权中间件 `requireCourseAccess` 取课程码是"网址里有就用网址的，否则看请求体"，
而这四个接口自己读请求体。**两边各读各的，中间件查的是生化，接口用的是英语。**
N2 的测试只发"只写请求体"这一种形状，中间件和接口恰好读到同一个值，所以一直是绿的。

同一处还有一条更隐蔽的：请求体里的课程码写成数字 `13000`，中间件只认字符串，
认不出就当成"没传"放行——检查整个跳过。今天后面查课程恰好会失败才没建出东西。

### 顺带查出来的

评估这一条时发现错题本也漏了：**撤销授权后，带课程码请求是 403、筛选项也滤了，
唯独不带课程码的列表没有按授权过滤**，把那个学科的错题连同题干、答案、解析原样列出来。
而学员端错题页挂载时恰好先发一次不带课程码的请求。

`n2-grants.sh` 里本来有一条「错题本筛选项不含已撤销学科的题型」——**它一直是空转的**：
测试里的学员从没交过卷、一道错题都没有，过滤不过滤结果都是 0。「不再提示进行中的练习」
那条同理（学员从没开过练习）。两条都是标准 §1.1 的"装饰品"，现在测试先造出错题和进行中的
练习、断言它们存在，再断过滤。

### 修法

- 中间件把验过的课程码放进 `c.get('courseCode')`，四个接口只从那里取，不再自己读请求体；
- 网址和请求体都带、但不一致 → 400 `course_code_mismatch`；请求体里不是字符串 → 400；
- 错题本列表加上与筛选项同一个 `accessibleCourseFilter`；错题页课程码取定之前不发请求。

### 教训

**校验和使用必须是同一个值，而且最好是同一个变量。** "中间件读一遍、接口再读一遍"
在两边读法一致时看不出问题，一旦读法有分歧（优先级、类型判断、默认值），校验就变成了
对另一个值的校验。9.3 节"中间件里取不到路由参数"是同一类：中间件自以为在查，其实没查到
接口要用的那个东西。写按前缀挂的中间件时，让它把验过的值交给接口，而不是让接口自己再取一次。

## 十六、给测试分开了本地库，照样不能并行：wrangler dev 的打包产物在 .wrangler/tmp（CR 第一批，2026-09-27）

### 症状

为了少等，把新套件 `cr-auth-limits.sh` 改成用自己的本地库目录（`--persist-to .wrangler-cr-auth`），
和另一套不起服务的 `cr-h2-publish.sh` 同时跑。后者全绿，前者卡在第一段一动不动，七八分钟没有输出，
也不报错。dev 日志最后一行：

```
✘ [ERROR] Could not resolve ".../worker/.wrangler/tmp/bundle-VntAWl/middleware-loader.entry.ts"
```

### 根因

`--persist-to` 只管本地数据（D1、KV）放在哪。**`wrangler dev` 的打包产物固定写在项目目录的
`.wrangler/tmp`**，不跟着 `--persist-to` 走。另一套开头照惯例 `rm -rf .wrangler`，把正在跑的服务的
打包目录删了；服务在下一次重载时找不到入口文件，请求挂住。这和第四节"杀服务要杀整个进程组"那条
提到的"已删除的构建临时路径"是同一个目录。

### 教训

**"各用各的库"不等于"互不干扰"。** 并行之前要把每一套会写的共享位置都列出来：
本地库、`.wrangler/tmp`、`worker/.dev.vars`（每套都往里写自己的密钥、收摊时删掉）、`worker/public`
（vite 构建会清空它）、`worker/seed/`（导题库脚本会重新生成）。这次只隔开了第一个。
M9（回归并行化）要把这些都隔开才做得成；在那之前，所有套件一律串行跑。
（M9 做完了：`test/run-all.sh` 给每套一份沙箱，真做时又冒出三处共享，见第二十节。）

## 十七、变异验证把被测代码的依赖也一起换回去了，新断言"照样绿"（CR-M2，2026-09-27）

M2 给改密码页加了"存下服务端换发的新令牌"，ui-smoke 相应加了两条：改完密码换个页面，
仍在登录状态、接口照常可用。整批做变异验证时，把这一批动过的服务端和前端**一起**换回旧版，
这两条却是绿的。

不是断言没用：旧服务端改密码**本来就不废旧令牌**，旧页面不存新令牌也不会出事。
被测的是"前端存新令牌"，而让这件事变得必要的是"服务端废旧令牌"——把两层一起换回去，
测的前提就没了。只换前端、服务端保持新版再跑一次，两条都红（被踢回 /login）。

**变异时只动被测的那一层，它依赖的东西保持新版。** 一批改动跨了几层时，"整批换回旧版跑一次"
只能证明服务端那些断言有用；前端那几条要单独再跑一轮。

## 十八、线上实测一次都没跑成过，四个里程碑没人发现（CR-M4，2026-09-30）

### 症状

CR 评估 M4（上传出题的 AI 答案、解析从没对真模型跑过）时去翻 `prod-e2e` 的运行记录：
XLearn 分支上只有两次（#4、#5），都是推送触发，都红在第一步——`WORKER_URL 还没填`。
N0 把老站地址清空，留了一句"首次部署后填进来再用"，之后没人填。所以不只是上传出题，
英语那条真模型链路（作文批改、错题分析）从复制过来到现在也一次都没在线上验过。

地址填上也跑不通：脚本建探针账号时不带学科授权，而 N2 之后没有授权的学员组卷是 403。

同一次评估还查出两件同类的：

- 部署只写「图片解析」「教学」两档 AI 配置，N7d 新加的「文字解析」没人写。除非管理员在后台
  手动配过，线上传 docx 让 AI 出答案会退回图片解析那档——一个 OCR 模型——去干文字活。

（地址、授权规则、AI 配置分档），它自己一行没改，所以也不会因为"改了这个文件"被推送触发。
它依赖的每一样变了都应该让它红，而它根本没机会红。

- 本地套件 `prod-e2e-local` 把流水线里的 `get-admin-token.sh → configure-ai.sh → prod-e2e.sh`
  原样对本地服务 + 替身跑三遍（全新库；有残留章节且探针授权被撤；文字解析没配），进全套回归。
- 部署写 AI 配置的逻辑从 YAML 搬进 `scripts/ci/configure-ai.sh`，本地能真跑；文字解析只补不改。
- 加了删除内容组的接口和校对页按钮，上传撞 id 的提示改成指向它；实测传完测试章节也靠它收拾。

### 教训

**只在线上手动跑的检查，要有一个平时就会跑的本地版。** 替身证明不了真实服务怎样（第二节），
但证明得了"这个检查本身还跑得通"——这次缺的是后者：它连对着替身都没跑过。
**报错和提示里指给人的路，要有测试走一遍。** "请先在后台删除它"这句话没有任何测试会去点那个
不存在的按钮；现在 `n6b-upload` 删完之后会用同一个 id 重传一次，证明提示说的那条路走得通。

## 十九、作文"批改成功、0 分"：断言写的是直觉，日志又没留证据（CR-M11，2026-09-30）

### 症状

线上实测 #6：英语作文返回 `{status: graded, total: 0}`，实测脚本红在"作文批改返回 0 分——这段是
通顺英文，八成是没读懂模型的回复"。同一次的 20 条错题分析全部成功。日志里只有一个 `total: 0`。

### 当时分不清的两种可能

- 模型把提示里的 JSON 示例原样抄了回来。示例里维度分用 0 占位、评语留空，抄回来是一个形状完全
  合法的"0 分"——解析只要读到一个维度分就算成功，于是照单全收，学员静默拿到 0 分；
- 随机抽到的作文题和实测那篇固定作文（讲网课）不是一个话题，模型按跑题给了 0 分——合理结果。

两种在当时的日志里长得一模一样。

### 实际是哪种

加了日志之后的实测 #7：题目是 "Green Transportation" 征文，模型五个维度全给 0，每个维度都写了
评语（"未覆盖题目要求的写作要点，偏离主题"……）。是跑题判分，不是抄示例。顺带看到模型一判
跑题就全维度 0，并给每个维度找理由，有的并不属实（约 90 词的通顺短文被说成"字数严重不足"）。

### 修法

- 服务端把"维度分全 0、评语和建议全空"当成没读懂（`ai_bad_shape`，可重试）——不管 #6 是不是它，
  这种回复都不是批改结果；替身加了 `/echo/` 专门模拟；
- 实测脚本把作文题目、各维度分、评语打进日志；断言从"不能是 0 分"改成"0 分要带理由"，
  "总分 ≠ 客观分"改成"总分 = 客观题 + 作文分"；
- `essay-parse.mjs` 原来测的是把取分段落**抄过去**的一份，`tutor.js` 改了它看不见，改成直接测
  `tutor.js` 导出的函数。它原来那条"真零分不误判"的输入是分数全 0、没有评语——正是要拦的形状。

### 教训

**"这段是通顺英文，不该是 0 分"是直觉，不是系统承诺的性质。** 卷子是随机组的，作文题不固定，
跑题给 0 分本来就对。断言要写系统承诺的东西：批改了就要带理由、总分等于各题之和。

**线上实测红了要能当场说出原因，日志里得有证据。** 只打一个分数，红了只能猜；把题目和评语打出来，
下一次一眼就分得清。线上实测一次要花钱，"再跑一次看看"比多打几行日志贵得多。

**给模型的 JSON 示例，想一想原样抄回来会被当成什么。** 用 0 和空串占位，抄回来就是一个合法的
"0 分"；解析要能认出"什么都没说"的回复。

## 二十、回归并行化：第十六节列了五处共享写入，真做时又冒出三处，外加两处环境的坑和一次没查清的崩溃（CR-M9，2026-09-30）

### 起因

全套回归串行一轮要 45 分钟（实测 45 分 28 秒），推送前必跑。时间几乎全花在 `npx wrangler d1 execute` 上：一次约 2.4 秒
（起 node、加载 wrangler、起 workerd），一套几十到上百次，服务本身几秒就起来了。
第十六节已经知道并行的拦路虎是 `worker/.wrangler/tmp`，当时列了五处共享写入：本地库、
`.wrangler/tmp`、`.dev.vars`、`worker/public`、`worker/seed`。做法是给每套一份 repo 的最小副本
（沙箱），这五处自然都隔开了。真做的时候又冒出三处。

### 1. `scripts/` 软链不得：Node 顺着链接找回原仓库

沙箱第一版打算只复制 worker 里的东西，`data/`、`scripts/` 软链回原仓库。但
`build-seed-sql.mjs`、`build-bank-assets.mjs` 都用 `import.meta.url` 推仓库根目录，而 **Node 加载
模块时按真实路径算 `import.meta.url`**（除非加 `--preserve-symlinks-main`；拿一个探针脚本试过，
经软链调起时推出来的是链接指向那边的根目录）——从沙箱里调起的脚本会顺着链接找回原仓库，
把种子写回原来的 `worker/seed`、把资源拷进原来的 `worker/public/bank`。n6-content 重新生成
英语种子时先删同名文件再写，这期间同时在跑的套件去 `ls seed/*…sql` 就可能扑空。
（这一处是设计沙箱时查出来的，没有真让它发生。）四个目录加起来 5MB，全部复制；
只有 `worker/node_modules` 软链，它只读不写。

### 2. wrangler dev 的调试端口：不指定就从 9229 往上探

每个 `wrangler dev` 除了服务端口，还绑一个调试端口，不指定时从 9229 往上找一个空闲的
（`memoizeGetPort`）。"探的那一刻空闲"和"真绑上"之间有空档，几套同时启动就可能探到同一个，
后绑的起不来——报错会是"服务 150 秒没就绪"，看起来像网络或端口表的事。
这一条是读 wrangler 源码看出来的，没有真撞上过；但它和第十六节是同一类（串行时不存在、并行时偶发），
撞上了很难查，所以提前隔开：run-all.sh 在沙箱的 `wrangler.toml` 里给每套指定一个（9300 起）。
并行时在 `/proc/net/tcp` 里能看到 9301、9303……各自在监听，说明这个端口确实每套都要占一个。

### 3. 本机没有 `ss`：各套"等端口释放"的循环从来没等过

各套起服务前都有一段

```bash
for i in $(seq 1 20); do ss -ltn 2>/dev/null | grep -q ":$PORT " || break; sleep 1; done
```

本机没有 `ss`。命令不存在时 `2>/dev/null` 吞掉报错、grep 什么都匹配不上，循环第一轮就 break——
**这段等待从写下那天起就没生效过**，而它看起来一切正常。run-all.sh 开跑前要查"端口有没有被
上一轮残留的 workerd 占着"，照抄这一句就是个摆设；改成直接读 `/proc/net/tcp`，读不到就明说
"这项检查这次没做"。（各套里那句没改：单独跑时端口被占，会以"服务起不来 + Address already in use"
报出来，是吵的失败，不是静的。）

### 4. "wrangler dev 启动要 100 秒"复现不出来；真正怕代理挂住的是 `d1 execute`

CLAUDE.md 原来写着"wrangler dev 启动要 100 秒以上，因为要连几个被拒的地址、重试到超时"。
M9 本想用两个开关（`WRANGLER_SEND_METRICS=false`、`CLOUDFLARE_CF_FETCH_ENABLED=false`，
分别关掉用量统计上报和取 `Request.cf`）去掉这段等待，动手前先量了一下：

| 场景 | wrangler dev 就绪 | 一次 d1 execute |
|---|---|---|
| 现在的代理（立刻拒绝），设不设开关 | 3–5 秒 | 约 2.4 秒 |
| 假代理（只接连接、永远不回），不设开关 | 6 秒 | **结果打出来后进程不退出，240 秒封顶被杀** |
| 假代理，只关统计 | 5 秒 | **120 秒封顶被杀** |
| 假代理，只关 cf | 3 秒 | **120 秒封顶被杀** |
| 假代理，两个都关 | 2 秒 | 2.3 秒 |

启动慢复现不出来：代理现在是立刻拒绝；就算挂住，setupCf 也有 3 秒超时（dev 日志里能看到
`Unable to fetch the Request.cf object! … TimeoutError`，然后照常启动）。真正怕代理挂住的是
`d1 execute`：它退出前要等那两处外呼，**两个开关缺一个都会挂住**。一轮回归要调几百次 d1 execute，
代理哪天从"拒绝"变成"挂住"，不设开关就一轮都跑不完，而且看起来像"测试卡住了"。
所以 run-all.sh 两个都关；150 秒的就绪等待是上限不是固定等待，留着。

### 5. 浏览器实测全挂在 launch：TMPDIR 太长

最后带 `--ui` 跑的那一轮，服务端 27 项全过，浏览器 6 套全部"没有小结"，都死在
`browserType.launch`，报 "Target page, context or browser has been closed"。不是沙箱的事：
那一轮我把 TMPDIR 指到了会话的草稿目录（85 个字符），Chromium 在 TMPDIR 下建进程单例的 socket，
Unix socket 的路径最多 107 字节，超了就起不来。换成默认的 /tmp，同样的沙箱 6 套全过。
拿不同长度的 TMPDIR 试过：61 个字符能起，62 个就不行。run-all.sh 开跑前加了一道检查：
队列里有浏览器实测、TMPDIR 又超过 61 个字符，就停下来说为什么。

### 6. 一次没查清的崩溃：n6b-upload 的 wrangler dev 跑到一半没了

最终那一轮，n6b-upload 前 75 条全过，之后 30 条全红：取值全是空的或 `000`，最后一条"跑完之后服务还在"
也是 `000`。dev 日志停在一次发布请求（422，正常结果）之后，末尾是一个**空的** `✘ [ERROR]`；
wrangler 自己的调试日志里只有每 10 秒一次的心跳，最后一次在崩溃前几秒，没有任何报错。
崩的时候，套件正在另起 `wrangler d1 execute --local` 读库，那两次读库都成功了。

单独重跑这一套，105 条全过；在此之前的三轮全量（并行、串行、并行）它也都是 105 条全过。

猜过是"dev 开着的时候另起进程读写同一个 SQLite 文件"，所有套件从第一天起就是这么用的。
造了个压力复现：dev 开着，一边不停登录（每次写一行），一边另起进程写库，240 秒写了 121 次，
没复现。**所以原因没查清，这里不把猜测写成结论。** 做了、建议做的：

- run-all.sh 在每套跑完后，立刻把它的 dev 日志拷进本轮目录，失败时在汇总里贴出尾部。
  各套 dev 日志写在 /tmp 的固定路径，这次的崩溃现场差点被随后的重跑冲掉；
- 建议（没在 M9 里做）：测试读库改成走 dev 服务自己的库。miniflare 带的本地接口
  `POST /cdn-cgi/local/explorer/api/d1/database/:id/raw` 能直接执行 SQL，这样不用再另起进程：
  少一个可疑的崩溃源，每次读库也从 2.4 秒降到毫秒级。

### 顺手做的：读库失败要看得见

各套原来各抄一份 `sql() { npx wrangler d1 execute … 2>/dev/null; }`。命令失败时报错被丢掉，调用方
拿到空串或一段报错 JSON，断言照常拿它去比——"读库失败"和"库里就是空的"在输出里长得一模一样。
n5-items 出过一次读回为空、重跑不复现，事后连是哪条 SQL 都查不到。现在收成一份
`test/lib/d1.sh`：stdout 照旧，失败时 stderr 多打一行"!! 读库命令失败：SQL 开头｜报错原文"。
SQL 错（没有这张表、违反约束）时 wrangler 的报错在 **stdout** 的 `{"error":{"text":…}}` 里，
stderr 只有一句代理提示——所以只接 stderr 是抓不到的。run-all.sh 把出现过这一行的套件
单独点名，哪怕它的断言碰巧全绿。

### 结果

| 跑法 | 墙钟 | 各项累计 | 结果 |
|---|---|---|---|
| 串行（`-j 1`） | 45 分 28 秒 | 45 分 24 秒 | 27 项全过，1274 条断言 |
| 4 路并行（第一版，凭感觉排的顺序） | 15 分 21 秒 | 55 分 49 秒 | 27 项全过，1274 条，逐套条数与串行一致 |
| 4 路并行 + 浏览器 6 套（最终版） | 16 分 5 秒 | 62 分 51 秒 | 33 项里 32 项过，1490 条；n6b-upload 的 wrangler dev 中途崩了（见第 6 条），单独重跑 105 条全过 |

并行时单套会变慢（n5-items 串行 484 秒、并行 606 秒）：串行时一套平均占 1.4 个核（负载 1.3），
4 路并行时负载到 7，4 个核已经占满，`-j` 再往上加不会更快。第一版的顺序是凭感觉排的，
cr-h2-publish（229 秒）和 n3-rebuild（201 秒）排在最后，别的都跑完了还要等它俩三四分钟；
现在按实测用时从长到短排。

### 教训

**隔离清单不能只按"谁写哪个目录"列。** 第十六节就是这么列的，漏掉的三处都是间接的：
脚本经软链会找回原仓库（要知道 Node 怎么算模块路径）、wrangler 会多绑一个端口（要知道它的默认值）、
检查命令本身不存在。每一处都拿实际行为核过一遍——探针脚本、`/proc/net/tcp`、`ss` 那一句的真实输出——
光读代码会以为没问题。

**优化之前先量。** 照着"启动要 100 秒"去优化，会在 wrangler dev 上找半天；量了才知道启动根本不慢，
会被挂死的是另一处。量的时候要把"坏情况"造出来（这里是一个永远不回话的假代理），
只在今天这个"代理立刻拒绝"的好环境里量，两个开关看起来毫无作用。

**偶发失败不能当 flake 放过去。** 重跑绿了只说明它不是必现；原因没查清就明说没查清，
并且把下一次查清要用的证据先留住。

**报错离原因越远，越要把原因写进检查里。** "浏览器被关掉了"和"临时目录路径太长"之间隔着
Chromium 的进程单例和 Unix socket 的长度限制，下一个人撞上时不会往那边想；与其在文档里提醒，
不如让执行器在开跑前把话说清楚。

**依赖外部命令的检查，命令不存在时要失败，不能"什么都没查到"。** `cmd 2>/dev/null | grep -q …`
在 cmd 不存在时和"查了，没有"输出一样。写这类检查时先确认命令在，或者读 `/proc` 这种不依赖命令的来源。

## 二十一、测试读库改走本地接口：按库名去问，它回的是另一个空库（CR-M12，2026-09-30）

### 起因

M9 之后回归并行一轮 16 分钟。那一轮一共 1404 次 `wrangler d1 execute`，每次 2.4 秒（另起 node 和
workerd），几乎就是全部的时间；第二十节第 6 条那次没查清的崩溃，崩的时候套件也正另起进程读库。
服务起来之后的读库，改成走 dev 服务自己的库，两件事一起处理。

### 本地接口按 database_id 找库，而 database_id 必须留空

miniflare 带一个本地接口：`POST /cdn-cgi/local/explorer/api/d1/database/<id>/raw` 能直接执行 SQL。
它默认开着（`X_LOCAL_EXPLORER` 默认 true；dev 日志里"检测到这是 AI 代理"那句只决定打不打提示），
所以 CI 里也能用。

列库接口回的 uuid 是空串——`wrangler.toml` 的 `database_id` 本来就必须留空（CLAUDE.md 四之二），
路径里拼不出来。于是试了按库名（`xlearn`）和绑定名（`DB`）去问：**两个都不报"找不到这个库"，
回的是 `no such table: users`**——接口给这个名字另开了一个空库。要是没先确认表在不在，
这条路会"跑通"，然后所有读回都是空的，看起来像是数据没写进去。

解法是只在 run-all.sh 的沙箱副本里把 `database_id` 换成全 0 的假 id。读库命令、dev 服务、
本地接口按同一个 id 找库，一边写、另一边读，两个方向都试过。真实目录不动，单独跑某一套照旧走命令。

### 一次给多条语句：接口只回最后一条的结果

`wrangler d1 execute --json` 一次给几条语句，每条回一个结果；接口只回最后一条的（每条都会执行）。
现有调用里多语句的只有 m4-smoke 两处，输出都丢掉了，所以调用方不用改；这一点写进了助手的注释，
d1-lib 里有一条"三条语句都执行了"。

### 连不上才退回，超时和看不懂不退回

助手在连不上时（服务还没起、已经收了，curl 退出码 7）退回命令——这是选路，不是兜底。
接口超时、回的东西看不懂，都算失败、不退回：退回去会把"服务卡死了""wrangler 升级换了接口"
藏成"读库照常成功，只是慢了点"，没有任何断言会红。d1-lib 用两个假服务（只接不回的、
回 404 纯文本的）钉住这两条；把"退回"改回去，对应的断言当场变红（7 种改法逐一试过）。

### 结果

| 跑法（4 路并行，带浏览器 6 套） | 墙钟 | 各项累计 | 读库助手走向 |
|---|---|---|---|
| M9 之后（全走命令） | 16 分 5 秒 | 62 分 51 秒 | 全部走命令 |
| M12 之后 | 11 分 52 秒 | 45 分 47 秒 | 接口 444 次、命令 159 次 |

34 项全过，1549 条断言，逐套条数与 M9 那几轮一致，外加 d1-lib 的 29 条。服务起来之后读库多的套件
快了一倍以上（n2-grants 161→65 秒，n6b-upload 215→48 秒）；墙钟现在卡在 n5-items（470 秒）——
它的读库大多发生在服务起来之前（旧库模拟），这条路没法走接口。

这一批回归里另外红过两次：一次查清了是测试自己的时序问题，一次没查清。

- **ui-subjects 的"学科切换器可见"是立刻数的。** 切换器要等"我的学科"接口回来才渲染，比侧边栏
  导航晚一拍；测试等到了导航就去数，负载高时就会数到 0（以前几轮都过，M12 第一轮红了这三条）。
  改成先等它出现（最多 10 秒），真不出现照样红。
- **n6-content 的"补完之后整套迁移还跑得过"红过一次，重跑、单跑、造负载复现（40 次）都没再出现。**
  那条检查把迁移的输出丢进了 /dev/null，只剩一个 0/1，事后不知道是哪个迁移、报的什么。
  改成红的时候直接报出迁移文件名和报错原文。原因没查清，也不排除和 M12 有关（那一段里走接口的读
  和另起进程的写交替进行）——造了"接口读紧接着命令写迁移"的复现，压满 CPU 跑 40 次没出现，
  所以不写成结论。

### 教训

**换一条路去问同一个东西，先证明问到的是同一个东西。** 按库名问接口"成功"了，问到的是一个空库。
验证的办法是一边写、另一边读，两个方向都做，而不是看它回了 200。

**选路要留下看得见的记录。** 两条路结果一样、只差快慢时，悄悄退回慢的那条不会让任何断言变红。
所以助手用 `D1_TRACE` 记下每次走了哪条路，run-all.sh 在汇总里摆出次数；哪天"走本地接口"
掉到 0，一眼就看得出来。

## 二十二、部署脚本搬家：搬之前没人能跑它，一跑就照出三个藏了很久的问题（CR-M8、M10、M13、M14，2026-10-01）

### 起因

`deploy-worker.yml` 715 行，大半是内联 shell，线上验证一段就 264 行。这些逻辑只有真部署时才跑得到：
本地没法跑，也没有测试。M8 要把它们搬进 `scripts/ci/`。

### 搬家本身：`set -e` 是隐形的

YAML 里不写 `shell:` 的 run 步骤，GitHub 用 `bash -e {0}` 执行，一条命令失败整步就停。
搬进脚本后由 `bash 脚本` 执行，**默认不带 -e**。正文一个字不改，行为也会变：原来会停下的失败
（比如线上验证里那几条没加 `|| echo` 的 curl）会被跳过去接着跑。所以每个搬出来的脚本开头补
`set -e`，它不是新规矩，是把原来看不见的那个开关写出来。

"一字未改"要拿出证据：用脚本从旧 YAML（`git show HEAD:`）抽出每段 run、去掉缩进，和新脚本
`set -e` 之后的部分逐字比，8 段全一致；步骤的其余行（name、env、working-directory、注释）也逐行一致。
比对脚本自己先故意改坏一个字，确认它会报"不一致"。只搬不改单独一个提交，行为改动在下一个提交里。

### 评估时照出来的：新库上学员一个学科都没有（M13）

为了在本地彩排这些脚本，要先想清楚"新库上按部署顺序跑一遍会怎样"。N2 的补授权迁移只给
**迁移那一刻已有的**学员补授权，跑一次就上门闩；部署里建 T001–T010 时不带学科。线上没事，
是因为这 10 个账号比 N2 早。本地新库实测：迁移 → 建 T001 → 再跑一遍迁移，T001 的授权是 0 条，
门闩已合上，以后也补不上。重建库、预发环境都会撞上，而且线上验证那条"既有学员 T001 有授权"会红。

### 彩排照出来的：把某一时刻的状态当成不变量（M14）

线上验证里"英语 20 套试卷全部已发布"在 H2 之前没问题——部署每次都跑 publish-all.sql，全部放回去。
H2 之后撤回会保留，管理员撤回任何一套英语卷，之后每次部署都会红。彩排第一次跑（改之前）还多照出一条：
**"解析存疑记录已清零"**。撤回的那章种子一变，重导把它的存疑插回来，放行不处理没发布的章节，
存疑就留在那里等人看——这是正常状态，断言却红了。上传内容没核完时也一样。

两条换成真正要守的：部署前后每一章的发布状态一样（导题库前读库记下，验证时从后台接口取，两边
不同源，多了少了都红）；已发布的章节没有未处理的存疑（发布那道门本来就要求清零，重导插回来的由
放行处理，哪一步漏了这里就红）。

### 差一点踩上的：换掉"每次都写"的动作，哨兵会一起失效（M10）

AI 配置改成只补不改很简单，但线上验证的写入哨兵读的就是「教学」那档的更新时间——靠的是它每次部署
都被重写。只改配置脚本、不换哨兵的话，下一次部署哨兵就会报"写入未恢复"（10 分钟窗口外），而且
这件事本地发现不了，因为以前根本没有东西在本地跑线上验证。

新哨兵是 admin 这次登录写下的"最后登录时间"：取令牌那步记下发请求的时刻，最后登录时间不早于它
（留 60 秒时钟差）才算这次写入落了库。登录**成没成功**当不了哨兵（额度用尽也放行），
它顺手写的那一笔可以。判据也比原来的"10 分钟内"紧：原来 10 分钟内有人在后台改过配置就能混过去。

### 彩排套件 deploy-local

新库上按部署顺序真跑那些脚本三次：第一次上线 → 管理员发布英语 → 平常一次 → 管理员撤回一章、改两档
AI 配置、撤一个学员的一个学科，另有两章种子变了 → 迁移重跑加两章重导。要求线上验证全过、管理员
改的东西都还在；再反过来证明线上验证会红（最后登录时间没写进去、部署弄丢或多放一章、已发布的章节
带着存疑、没有部署前的记录）。

**先在改之前跑**：15 过 12 败，M10（两档模型被冲回默认值）、M13（T001 没有授权）、M14（19 套、
存疑 8 条）都在里面；改完 28 条全过。顺带发现几个脚本用 `/tmp` 下的固定文件名（login.json、
users.json……），而 deploy-local 和 prod-e2e-local 会同时跑 get-admin-token.sh，改成各用各的
`mktemp -d`。

第一次进全套回归时它被判成"没有小结"：28 条全过，但小结写成了"通过 28, 失败 0"，而执行器认的是
"28 通过, 0 失败"。执行器不认就不算过——第二十节加这道判定，防的正是"格式不对、看着像过了"。

调 Cloudflare 接口的四步（账号、子域名、建库、Worker 密钥）和 wrangler deploy 本地跑不了，
这几个只有逐字比对和真实部署作证。

### 教训

**只在线上跑的代码，等于没测过的代码。** 把它搬到能在本地跑的地方，第一次跑就照出三个问题，
而它们在线上藏着，是因为线上那个库的历史刚好把它们盖住了（账号比 N2 早、一直没人撤回过英语卷）。

**测部署要测"连着两次、中间有人改过东西"。** 单次部署全绿说明不了什么：M10、M14、H2 都是第二次
部署才出事，而且都要求中间有人在后台做过合法的操作。

## 二十三、导入过的题库文件不许改：先删后插换成只插不改，测试里有两条把要消灭的行为写成了"正面对照"（CR-H4、H2 根治，2026-10-01）

### 规矩

用户定的：**导入过的题库文件不许改**。内容要改，在后台把旧题停用，用新的内容组编号加一个新文件。
停用按单题；可以恢复，恢复后是草稿，要重新发布；停用的题学员错题本里不显示、不计入错题数。

我原先的方案是"按题合并"（文件改了的题以文件为准、其余保留后台的修改），要逐题判断是谁改的、
还得处理"文件改了一道已确认的答案"这类冲突。规矩一定，这些冲突都不存在了：导入之后文件就是只读的。

### 改之前先照红

新套件 `h4-seed-guard` 先对改之前的代码跑：**19 过 35 败**。最要紧的三条：

- 英语那章的文件改了一个题干 → 那道题在后台改过的题面被冲回文件里的版本（读回来是 "French"）；
- 生化那章（学员做过）的文件改了 → 导题库外键报错，整步退出 1，部署卡在这里；
- 绕过脚本、手动执行同一个种子文件 → 照样"成功"，后台的修改照样被冲掉。

### 三道关

1. **推送时**（`check-bank-files.sh`）：拿推送前的版本比，已有的题库文件、题目图片改了、删了、改名了都红，
   代码都不部署。图片只能在这里拦：它随前端上传，改了图已导入的题立刻换图，导题库那一步看不见。
2. **导题库时**（`seed-if-changed.sh`）：按内容组编号记指纹。导过、变了的拒绝，库里一行不动，写进拒绝清单，
   由线上验证报红点名——这一步本身不失败，不然后面的初始化和线上验证全被跳过。
3. **种子 SQL 本身**：只插不删，最后一条是普通 INSERT 的指纹。有人绕过脚本手动执行，也只会撞主键整体失败。

### 旧指纹的两个隐患（这次一起没了）

- 按**种子文件名**记，而文件名带序号（`english-020-…`）：中间插一个新文件，后面所有文件的名字都变，
  等于"全部变了"、全部重导；
- 按**生成出来的 SQL** 算：改一下生成器（加个注释都算），所有种子都"变了"。

旧机制下这两件事都等于一次全量先删后插，正好撞上 H4。现在按**内容组编号**记、算**题库文件本身**的字节。

### 上线那一次：补记指纹

线上 21 章只有旧的按文件名的记录。补记要三个条件同时成立：库里有这一章、有旧记录（按 `<学科>-<三位序号>-<编号>.sql`
的模式找，序号会变，不按现在的文件名找）、库里的题目编号和文件对得上。补记之后删掉旧记录，所以只会发生一次。
`data/` 最后一次改动在 N6，之后部署过多次，线上内容和文件一致——这是"补记是准的"的依据，不是假设。

### 测试里两条"正面对照"断的正是要消灭的行为

- `n6-content` 有一条"改回种子来源之后重导又能成功、哨兵被换回种子里的标题"，当初是给 origin 护栏写的正面对照：
  护栏不能把正常的重导也挡死。规矩一变，"正常的重导"本身就是要消灭的行为——翻成"再执行照样整体失败、哨兵还在"。
- `rich-text.test.mjs` 有一条"清题时连资源一起清"（断种子里有 `DELETE FROM question_assets`）：先删后插时不连资源一起删
  会留孤儿行。只插不删之后反过来断"种子里一条 DELETE 都没有"。

这两条在全套回归里一红一绿：rich-text 那条是全套跑出来的（我改种子语义时没想到 node 单测里也断了它），
n6-content 那条是改之前就找到的。`cr-h2-publish` 整套测的是放行标记，放行拆了它跟着删；它守的"撤回的不被放回去"
由 M14 的发布状态比对和 `deploy-local` 接着守。

### 单题停用

`questions.status` 的三值 CHECK 改不动，同 `answer_state` 一样单开两列（`retired_at` / `retired_by`）。
抽题判据加第三个分量——**只改了 `pickableSql` 一个函数**，七处查询自动跟上，这就是当初把它收成一个函数的意义；
错题本的判据同样收成一个（`wrongItemVisibleSql`）。停用时已发布的退回草稿，不留"已发布但停用"：否则凡是数已发布
题数的地方都得各自再排除一次停用。看板新增 `retiredButPublished`，线上验证断它是 0。

把四处改坏（抽题判据去掉停用分量、错题本判据恒真、整卷发布不跳过停用、单题发布不拦）一起跑一遍 n6-content，
红了 7 条——**但"抽题判据去掉停用分量"那一处没有一条是因它而红的**。"停用后题型清单少一道"看起来在测抽题判据，
其实测的是"停用时退回草稿"：草稿本来就抽不到，判据里那个分量有没有都一样。补了一条直接改库把停用的题弄回
已发布、断抽题照样排除它（看板同时报出"停用却已发布"），再单独把那个分量去掉跑一遍，红的正好就是这一条。
**两道保险叠在一起时，测试只碰得到外面那道；里面那道要单独造一个只有它能挡的状态去测。**

### 本地踩到的两个小坑

- **照红的环境本身先要对。** 测试自己搭的仓库副本起初只拷了 `worker/src/lib`，而生成器用的校验又引 `graders`、
  `normalizers`——旧代码那一轮先报"生化种子生成失败"，看起来像旧代码的毛病，其实是副本不全。照红之前先证明
  "照红的那个环境跑得通"，否则红的是环境。
- **`ps | awk '/[关]键词/'` 一样会匹配到自己。** 我用它找测试进程，命令行里恰好也有那个词，把执行这条命令的 bash 杀了
  （退出码 144）——和 CLAUDE.md 里 `pkill -f` 那条是同一个坑，换个写法照样踩。按 PID 找、或者匹配一个只在目标里出现的串。
- 变异验证时让脚本"等快照拍完就把源码改回去"，等待条件写错了路径（沙箱是 `<套件>/repo/worker`，不是 `<套件>/worker`），
  条件永远不成立，源码就一直停在改坏的状态——是我回头去查才发现的。**改坏源码的窗口要自己盯着关上，不能交给一个没验证过的条件。**

### 教训

**规矩变了，先去找"把旧规矩写成正面对照"的断言。** 它们看起来是在保护正常功能，实际上是在保护要消灭的行为；
不找出来翻掉，新代码会被它们拦下来，更糟的是有人为了让它们变绿把新规矩改回去。

## 二十四、数据恢复：备份能不能恢复，要拿刁钻的数据往返一遍才知道（CR-M6、M7、M15、M16，2026-10-01）

### 做了什么

用户选的方案：每次部署动库之前加密备份一份，存成流水线附件留 90 天；七天内的事故走 D1 时间旅行。
恢复都走 GitHub 上手动触发的流水线（用户不在本机跑 wrangler），演练在一次性的库上真走一遍。
细节见 `docs/数据恢复手册.md`。下面是做的过程中踩到的，按"差点就上线了"的程度排。

### 1. 线上导出会把整库的下载链接打进日志

写备份那一步之前先翻了 wrangler 的源码：`d1 export --remote` 导完会打一行
"You can also download your export from the following URL manually. This link will be valid for one hour: <链接>"。

仓库是公开的，流水线日志谁都能看——一小时之内，任何人点开那次部署的日志就能下载整库明文：学员作答、密码哈希、加密后的 AI Key。
备份文件本身加了密，日志里却躺着明文的下载地址。

现在导出的输出只进临时目录，失败时先把链接涂掉再打。演练里有一条断言：备份日志里一个 `http` 都没有。

### 2. 导出器把"换行 + 字面的 \n"写走样，而"导回去再导出比一比"天然看不出来

**往返测试 `restore-local` 第一次跑就红了。** 一条存疑记录里既有真换行、又有字面的反斜杠 n，导出再导回之后，字面的 `\n`
也变成了换行。

原因在导出器（miniflare 的 `outputQuotedEscapedString`）。它把文本里的换行写成 `\n`、回车写成 `\r`，整段包一层
`replace(…,'\n',char(10))`。同一段文字里要是本来就有字面的 `\n`，导回去时分不清，一起被替换。SQLite 自己的 `.dump` 遇到
这种情况会换一个文本里没出现过的占位符，这里照着移植时把这一步漏了。生化题的公式（`\nu`、`\neq`、`\nabla`）、AI 写的解析、
学员的作文，都可能撞上。

**更要紧的是怎么发现的。** 我原本以为最硬的核对是"导进去再导出来，和备份逐字节比"。可走样之后的值再导出，写法和原来一模一样——
同一个编码器把两个不同的值编成了同一串，拿它的两次输出去比，永远相等。抓到它的是另一条断言：把那几行**的值**从源库和新库各读一遍对比。
这和"期望值和被测值不能同源"是一回事：拿同一个导出器的两次输出互相印证，等于没印证。

修法：备份时把这种值从库里找出来（同时有换行或回车、又有字面 `\n` 或 `\r` 的文本），按主键定位，用十六进制原样写成
`UPDATE … = CAST(X'…' AS TEXT)` 附在导出文件末尾；导入后逐个核对（"核对三"）。manifest 的 `fixups` 记着补了几处，
备份里补丁丢了、对不上数也会红。

线上的导出是不是同一个毛病，演练（`d1-drill`）第 4 段专门放了一条这样的文本去试。演练 #1（2026-10-01）：
带着补丁导进新库，那条文本一个字节都没变。线上导出器自己会不会写走样，这一次没有单独拆开验证——补丁按内容找、
找到就补，两种情况下结果都对，所以没再为它多跑一轮。

### 3. 本地导入会把建表语句里的注释剥成空行

"再导出比一比"第一版比的是整个导出文件，在真实大小的库上报"10 行有出入"。一看全是建表语句：源库的建表语句里留着
迁移文件的注释，导进新库时 wrangler 把注释剥成了空行。数据一行没变。

和第十节是同一个现象（本地和线上对注释的处理不一样）。现在只比数据行（`INSERT`），建表的对不对由逐表行数那一道兜着。

### 4. D1 的两处限制，报错都看不出原因

- **复合查询的项数有上限。** 数各表行数用一条三十几项的 `UNION ALL`，报 `too many terms in compound SELECT`。
  改成每条语句十个标量子查询。
- **`wrangler d1 execute --json` 失败时，错误写在 stdout**（`{"error":{"text":…}}`），stderr 里只有一行代理告警。
  第一版报错只带 stderr，打出来是"读库失败：▲ WARNING Proxy environment variables detected"，完全看不出原因。
  现在两边都带。

### 5. 删掉一条快照检查，后面一条悄悄变成恒红（M16）

H4 之后"内容要改就加新文件"成了正规做法，线上验证里的"英语 20 套 / 1020 道"就变成会拦正常操作的快照。
- **先照红**：部署彩排里按正规做法加一个英语文件，旧验证当场红——20 套（实际 21）、1020 道（实际 1071）。
- **换法**：改成"仓库里每个题库文件的章节都在库里、题数和文件一致"，期望从文件现算。

**换完再跑，冒出一条没动过的检查红了**：「存疑题确实被排除在可抽题之外」。它拿 `QUESTIONS` 做比较，
而这个变量是被删掉的"1020 道"那条顺手算出来的。变量没了，bash 算术把它当 0，`已发布数 < 0` 恒假，这条悄悄变成恒红。
`deploy-local` 第一次跑就照出来了；没有彩排的话，它会在线上第一次部署时红，而且看上去像"存疑题漏出来了"。

那条检查本身也是快照（靠"现在恰好有题没发布"），一并删掉。**删一条检查之前，先看它算出来的变量后面有没有人在用。**

### 6. 部署找不到库，会悄悄建一个空库顶上（M15）

评估 M6 时读 `find-or-create-d1.sh` 发现的：按名字找不到就新建，接着导题库、建管理员和学员。线上验证照样全绿——
部署前 0 章已发布、部署后也是 0 章，"发布状态不变"成立。库被人在后台删了、或者 API Token 换到了另一个账号，学员数据全没了，
站点却像刚上线一样。

现在只有手动触发并勾「首次部署，允许新建数据库」才建。这段分支用假 Cloudflare 接口测（`d1-ops-guard`）：
找到、找不到不许建、找不到允许建、列表读不了，并且断"不许建的时候一个建库请求都没发出去"。

### 7. 时间差 8 小时（M7）

CR 里列了 4 处，扫出来是 12 处：页面各自原样显示世界时。授权到期日更糟：前端发"日期 23:59:59"、后端原样存，
被当成世界时比较，选 10 月 1 日到期，实际北京时间 10 月 2 日早上 8 点才失效；而且后端什么字符串都收，写错了也照存。

- 显示统一走一个函数；单测里加一道扫描，页面里直接显示 `xxx_at` 的就红（先在改之前跑：扫出 14 处）。
- 扫描是按名字猜的，误报过一次：日期选择框的状态变量恰好叫 `expiresAt`。改名成 `expiryDate` 解决，名字也更准——它装的是北京日期，不是库里的时间。

### 8. 又一次按命令行找进程，把自己的 shell 杀了

做 M15 的照红时，在同一条命令里先起假接口、最后按 `awk '/cf-api-stub[.]mjs 8889/'` 找它的进程号收掉。
`[.]` 这招只防"模式本身出现在命令行里"，而这条命令前面起进程那段写着原文 `cf-api-stub.mjs 8889`，照样匹配上，
连自己的 shell 一起杀了（退出码 144）。CLAUDE.md 第一节那条规矩补了一句：按参数位置精确匹配。

### 9. 本地拆句、线上整条发：D1 的长度上限本地永远跑不出来（2026-10-02）

第一次真部署之前核对时发现：备份查"会被导出改写的文本"，是 32 张表各一句、拼成一条 `--command` 发出去，
全库都有数据时 111 KB。翻 wrangler 源码：**本地的 `d1 execute` 先把命令拆成一句一句、逐句执行；线上是整条原样
POST 给 D1**。D1 文档写着一条 SQL 最长 100 KB；命令行一个参数最长 128 KB（实测 131071 字节可以、131072 字节报
Argument list too long）。拿那条 111 KB 的命令在本地跑——成功，测的是另一条路。核对三更糟：把要补回的原文
十六进制整个塞进一条命令，一段 24 KB 的文本就是 48 KB，处数一多就超。

线上那次部署是过了的（备份 3 秒，0 处要补回），但说明不了线上是按句还是按整条算长度——本地验证不了，就不赌：
- 新的 `scripts/ci/d1-query-chunks.sh`：一行一句，按字节攒批，每批不超过 40 KB（单句超过的自成一批），
  结果按原顺序合并，并核对"发了几句、回了几个结果"；
- 核对三改成只发"按主键取回十六进制"（一句一百来字节），期望值留在本地比，命令的长短和文本多长无关；
- restore-local 给 npx 套一层，记下每条 `--command` 的字节数。改之前：备份最长一条 58203 字节、导入最长 48557 字节，
  红；再把上限调到 12000 / 100 字节，备份的明文逐字节相同、核对三照样做完，补丁落空（主键对不上）照样报红。
- d1-ops-guard 的假 npx 像线上那样整条收下命令，测分批、顺序、单句超长、结果条数对不上、第 2 批 D1 报错。

**本地和线上走的不是同一段代码时，"本地能跑"只证明了本地那一段。** 和"替身的盲区"是一回事——这回的替身是
wrangler 自己的本地模式。
