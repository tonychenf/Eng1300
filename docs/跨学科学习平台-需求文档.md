## 1. 背景与目标

### 1.1 从哪里来：蓝本现状盘点

Eng1300 是一个**已经跑通并上线**的单学科系统，M1–M6 全部完成，线上端到端实测
15 条断言全过。它的能力清单：

| 能力 | 现状 |
|---|---|
| 题库 | 20 套自考英语真题 · 1020 道题 · 21 个考点标签 · 895 道可参与组卷 |
| 模拟考试 | 按七部分模板随机组卷、150 分钟限时、交卷即出客观题成绩 |
| 专项练习 | 三阶段自适应（摸底 / 强化 / 单考点），逐题即时反馈 |
| 错题本 | 判分时自动收录，连续答对两次自动订正 |
| 能力评估 | 统计层（时间衰减加权预测）+ AI 定性层，并列呈现 |
| AI 教学 | 作文批改、错因分析、答案讲解、能力评估四类调用 |
| 后台 | 题库校对发布、账号管理、学情看板、数据导出、AI 配置、系统参数 |
| 技术栈 | Cloudflare Workers + D1 + Hono / React 18 + Vite，单域名同时托管前后端 |
| 成本 | 全部落在 Cloudflare 免费额度内 |

**这套东西的产品逻辑与学科无关。** 组卷要考点多样化、练习要按掌握度加权、错题要连对
两次才算订正、AI 不可用时主链路不能塌——这些规则换成数学、政治、法律同样成立。

**但它的实现处处是英语。** 判分器里是英美拼写对照表，AI 提示词里写死"自考英语科目的
阅卷老师"，作文评分维度是"内容/语言/词汇/连贯/字数"，抽题单位是"阅读篇章"。

**这就是本次改造的全部工作量所在**：把"与学科无关的系统能力"和"某个学科特有的知识"
拆开，前者共享，后者下沉到学科自己的配置里。

### 1.2 要做成什么

一句话：**把 Eng1300 从"一门课的练习系统"改造成"一个能装下任意学科的学习平台"，
每个学科有自己的题库、解析和评价标准，共用同一套系统能力，账号跨学科统一、权限按
学科授予。**

具体拆成五条，对应用户提出的五点要求：

| # | 要求 | 本文档对应章节 |
|---|---|---|
| 1 | 跨学科学习平台，新增学科选择功能 | §3 架构决策、§5.3 学科选择与切换 |
| 2 | 不同学科独立题库 | §5.4 |
| 3 | 不同学科独立例题解析 | §5.5 |
| 4 | 不同学科独立评价标准 | §5.6 |
| 5 | 学科共享系统功能与设计思路 | §3.4、§4 学科能力包、§5.7 |
| 6 | 同一账号下按学科授权，权限由管理员设置 | §5.2 学科访问权限、§6 权限矩阵 |
| 7 | 所有报告按学科区分 | §5.8 报告的学科分层 |
| 8 | 独立部署 | §10 |

### 1.3 本期范围（In Scope）

- 学科作为一等公民：建模、管理、选择、切换、隔离
- 学科级访问权限：授予、撤销、有效期、审计
- 学科能力包：题型、考点体系、组卷模板、判分规则、解析规格、评价标准全部可按学科配置
- 现有七大功能模块（模考、练习、错题本、能力评估、历史记录、学情看板、数据导出）
  全部加上学科维度
- 英语作为第一个学科完整迁入，行为与现状一致
- 第二个学科（用于验证架构，学科待定见 §15）完整跑通
- 独立部署流水线与独立数据库

### 1.4 明确不做（Out of Scope）

| 不做 | 理由 |
|---|---|
| 学科之间的知识迁移分析、跨学科推荐算法 | 属于下一阶段，本期只做跨学科**数据汇总**（§5.9） |
| 学员自助注册、自助申请开通学科 | 权限明确要求"由管理员设置"，先做管理员授予 |
| 多租户（多个互不可见的机构） | 当前是单机构多学科，租户层会再加一层复杂度，没有需求支撑 |
| 移动 App | 沿用蓝本决策，只做响应式网页 |
| 付费/订阅 | 沿用蓝本约束：完全免费 |
| 题目的在线富文本编辑器 | 题库仍走"JSON 数据文件 → 种子 → 导入"管线，后台只做校对与发布 |
| 学科间的题目复用 | 题目归属唯一学科，不做跨学科挂载 |

### 1.5 成功判据

**新增一个与英语结构相似的学科（如"大学语文"），不改一行系统代码，只增加数据文件与
学科配置，就能完整跑通"组卷 → 模考 → 判分 → 报告 → 错题 → 练习 → 评估"全链路。**

这条判据是本次架构改造的唯一硬指标。达不到它，说明学科层没有真正抽出来。

## 2. 名词定义

在蓝本 `docs/prd.md` §2 的基础上新增和修订：

| 名词 | 定义 | 是否新增 |
|---|---|---|
| **学科（Subject）** | 平台的顶层分区，如"英语""高等数学""思想政治理论"。**学科是权限边界、数据隔离边界和报告边界**。不同学科的题库、考点体系、解析规格、评价标准互相独立 | 🆕 |
| **学科能力包（Subject Pack）** | 一个学科跑起来所需要的全部配置与知识的集合：题型、考点体系、组卷模板、判分规则、解析规格、评价标准、AI 提示词。见 §4 | 🆕 |
| 课程（Course） | 学科下的一门具体科目，如学科"英语"下的课程 `13000`「英语(二)/英语(专升本)」。**课程决定组卷模板和试卷规格**，一个学科可以有多门课程 | 修订：从顶层降为学科的下级 |
| 真题（Exam） | 一次考试的完整试卷 | 不变 |
| 部分 / 题组（Section） | 试卷内的一个大题。英语里它是"一篇短文 + 若干小题"，其他学科里可能只是一组同类题 | 修订：名称从"部分"泛化为"题组" |
| 题目（Question） | 最小作答单位 | 不变 |
| 考点（KnowledgePoint） | 题目考查的知识点标签 | 修订：**从全局共用改为按学科独立** |
| **例题解析（Explanation）** | 一道题的结构化解题说明。结构由学科定义，来源可以是原卷官方解析、人工录入或 AI 生成，各自有独立的审核状态 | 🆕（蓝本只有一个自由文本字段） |
| **例题（Exemplar）** | 学科自建的典型题目 + 完整解题过程，用于教学讲解，**不进入组卷与练习抽题池** | 🆕 |
| **评价标准（Rubric）** | 一个学科怎么算对错、怎么给分、怎么判掌握、怎么预测成绩的全部参数 | 🆕 |
| 模考（Exam Attempt） | 按试卷规格组卷、限时的一次完整测验 | 不变 |
| 练习（Practice Session） | 不限时、逐题反馈的一次训练 | 不变 |
| 掌握度（Mastery） | 用户在某个考点上的累计表现档案 | 修订：键从"用户 × 课程 × 考点"变为"用户 × 学科 × 课程 × 考点" |
| **学科授权（Subject Grant）** | 管理员授予某个账号访问某个学科的权限记录，含角色、有效期、授予人 | 🆕 |

## 3. 架构决策：学科放在哪一层

这是本次改造最关键的一个决定，后面所有的表结构、接口、页面都跟着它走。

### 3.1 现状：蓝本已经有半层隔离

盘点蓝本代码可以发现一件重要的事：**`course_code` 已经贯穿了大部分表**。

| 表 | 是否已有 `course_code` |
|---|---|
| `exams` / `questions` / `exam_templates` | ✅ 有 |
| `attempts` / `user_knowledge_mastery` / `wrong_items` / `assessments` | ✅ 有 |
| `sections` | ❌ 无（通过 `exam_id` 间接关联） |
| `knowledge_points` / `question_knowledge_points` | ❌ **无，全局共用** |
| `system_settings` / `ai_settings` | ❌ **无，全局单例** |
| `users` | ❌ 无（角色只有 `SUPER_ADMIN` / `USER`） |

也就是说，**题库和学情数据的隔离骨架已经在了，缺的是**：

1. 一个真正的顶层概念（现在的 `courses` 表只有课程码和课程名，没有学科归属）
2. 考点体系、系统参数、AI 配置的隔离（现在是全局的，两个学科会互相污染）
3. 权限维度（现在只有全局角色，没有"这个人能看哪些学科"）
4. 报告的学科过滤（后台学情看板**当前完全没有按课程过滤**，见 §5.8）

这个现状决定了改造是**加一层**而不是**推倒重来**——这也正是用户的原话："相当于这些
功能模块儿，在上面添加一层学科的架构"。

### 3.2 三种候选方案

**方案 A：学科即课程（把 `courses` 改名成 `subjects`）**

- 改动最小，`course_code` 直接当学科码用
- 致命问题：一个学科下确实会有多门规格不同的课程。自考的"高等数学"就有
  `00022 高数(工专)` 和 `00023 高数(工本)`，两者**试卷结构不同、分值不同**，但
  **考点体系、解析规格、评价标准完全一样，权限也应该一起给**。
- 按方案 A，它们只能是两个学科，于是考点要建两套、权限要发两次、报告要分两张 —— 这
  恰恰是本次改造要消灭的重复。**否决**。

**方案 B：学科 → 课程 二级模型（推荐）**

- `subjects` 为新的顶层表，`courses` 增加 `subject_id` 外键
- **学科**承载：权限、考点体系、解析规格、评价标准、AI 提示词、系统参数覆盖、报告边界
- **课程**承载：组卷模板、试卷规格（时长、满分、题量分值）、题库归属
- 英语学科下只有一门课程 `13000`，与现状完全兼容；高数学科下两门课程，各一套模板，
  共用一套考点与评价标准。

**方案 C：学科 → 课程 → 模块 三级**

- 没有需求支撑，纯增加复杂度。**否决**。

### 3.3 决定：采用方案 B

```
学科 Subject（权限边界 · 报告边界 · 知识体系边界）
  │  subject_id, code, name, status, 能力包配置
  │
  ├─ 考点体系 knowledge_points（按学科独立）
  ├─ 评价标准 subject_rubrics（判分 / 掌握度 / 能力评估参数）
  ├─ 解析规格 subject_explanation_schema
  ├─ AI 提示词 subject_ai_prompts
  ├─ 参数覆盖 subject_settings（覆盖全局 system_settings）
  │
  └─ 课程 Course（试卷规格边界）
       │  course_code, subject_id, 时长, 满分
       ├─ 组卷模板 exam_templates
       └─ 真题 Exam
            └─ 题组 Section
                 └─ 题目 Question ── 例题解析 Explanation
```

**学情数据的键**：`attempts` / `wrong_items` / `assessments` / `user_knowledge_mastery`
同时冗余存 `subject_id` 和 `course_code`。

为什么冗余而不是只存 `course_code` 再 join `courses` 取学科：

- 学科级报告是最高频的查询（学员每次进错题本、能力评估、历史记录都要按学科过滤）
- D1 是 SQLite，join 本身不贵，但**每次都 join 意味着每个索引都要带上 join 列**，
  而现有索引（如 `idx_wrong_user ON wrong_items(user_id, course_code, corrected)`）
  是按 `course_code` 建的
- 冗余一个 `subject_id` 列 + 一个复合索引，换掉所有报告查询的 join，是划算的
- 风险是两列不一致，用**建表时的外键 + 写入时统一走同一个函数**兜住，不允许调用方
  自己拼 `subject_id`

## 4. 学科能力包（Subject Pack）

### 4.1 为什么必须有这个抽象：蓝本里的九处硬编码

不做这层抽象，加第二个学科就要改下面每一处，加第三个学科再改一遍。这是本次改造
真正的工作量，也是最容易被低估的部分。**逐条列出来，改造完成时逐条勾销。**

| # | 位置 | 现状（英语写死） | 目标 |
|---|---|---|---|
| 1 | `worker/migrations/0002_bank.sql` | `questions.question_type` 有 `CHECK IN ('single_choice','fill_blank_transform','essay')`，只认三种题型 | 题型由学科声明，改为引用 `subject_question_types` |
| 2 | `worker/src/lib/grade.js` | 整个文件是英语判分：29 组英美拼写对照、`-ise/-ize` 等三条规则、`OUR_KEEP` 例外表 | 拆成「通用判分骨架」+「学科归一化器」，英语归一化器原样保留 |
| 3 | `worker/src/lib/tutor.js` | `SYS = '你是一位中国自学考试英语科目的阅卷与辅导老师…'`，四类调用的提示词全是英语语境 | 提示词模板按学科存库，运行时注入 |
| 4 | `worker/src/lib/tutor.js` | 作文五维权重写死在代码里：`content 0.30 + language 0.25 + vocabulary 0.15 + coherence 0.20 + length 0.10`，再 `/6*30` | 维度、权重、满分进 `subject_rubrics`，代码只做加权 |
| 5 | `worker/src/lib/mastery.js` | 掌握度分档阈值（≥3 题且连对 ≥3 为"已掌握"）与抽题权重（2.0/5.0/1.0/0.3）写死 | 进 `subject_rubrics`，代码读配置 |
| 6 | `worker/src/lib/paper.js` | 抽题单位固定为"篇章"，且要求篇章已发布题量**正好等于**模板题量 | 抽题单位按学科声明：`SECTION`（篇章级）/ `QUESTION`（单题级） |
| 7 | `worker/src/lib/practice.js` | 两处写死 `q.question_type != 'essay'` 排除作文 | 改为读学科配置的"不进练习的题型"清单 |
| 8 | `worker/migrations/0002_bank.sql` | `knowledge_points` 表无学科列，全局共用；`ai_settings.purpose` 只有 `PARSING`/`TUTORING` 两行全局配置；`system_settings` 是全局扁平 KV | 三者都加学科维度，全局值作为兜底 |
| 9 | `worker/src/routes/admin-stats.js` | `/students` 和 `/overview` 的聚合查询**完全没有课程过滤**，跨全库统计 | 加学科过滤 + 单独的跨学科汇总接口 |

另有两处不在代码里但同样要按学科拆的：

- `data/PARSING_GUIDE.md` 是英语真题的解析规范（篇章、选项、写作提示）
- `scripts/build-seed-sql.mjs` 的 `COURSE_ALIAS` 和 `flaggedOrders()` 的中文题号正则

### 4.2 能力包的内容清单

一个学科要跑起来，必须提供以下七块。**前五块是纯数据，后两块可能要写代码。**

| 块 | 内容 | 载体 | 必填 |
|---|---|---|---|
| ① 学科元信息 | 学科码、名称、简介、图标、排序、状态 | `subjects` 表 | ✅ |
| ② 考点体系 | 考点标签树（可分层：一级/二级），每个考点的名称与分类 | `knowledge_points`（加 `subject_id`） | ✅ |
| ③ 题型声明 | 本学科用哪些题型，每种题型：是否客观题、是否进练习、是否需要 AI 判分、作答控件类型 | `subject_question_types` 表 | ✅ |
| ④ 评价标准 | 判分容差、主观题评分维度与权重、掌握度分档阈值、抽题权重、能力评估参数、及格线 | `subject_rubrics` 表（JSON） | ✅ |
| ⑤ 解析规格 | 例题解析的字段结构（如数学的"步骤/公式/易错点"）、AI 生成解析的提示词模板 | `subject_explanation_schema` + `subject_ai_prompts` | ✅ |
| ⑥ 判分归一化器 | 把学生答案和标准答案折成可比形式的函数（英语的英美拼写、数学的数值容差与等价式） | 代码：`worker/src/subjects/<code>/normalizer.js` | 视学科 |
| ⑦ 抽题策略 | 抽题单位（篇章级/单题级）与候选条件 | 声明式优先；特殊需求才写代码 | 视学科 |

### 4.3 声明式与代码插件的边界

这条边界划在哪里，直接决定了 §1.5 的成功判据能不能达成。

**原则：能用数据表达的一律用数据；只有"语义判断"才允许写代码。**

- **纯数据即可**：新增一个"大学语文"学科——题型是单选/多选/填空/简答，判分是文本
  精确匹配 + AI 主观题评分，考点是自己一套，解析结构是"考点出处/采分点/易错点"。
  这类学科**零代码**。
- **需要一个归一化器**：数学——`3.14` 和 `3.140` 要算对，`1/2` 和 `0.5` 要算对，
  `x^2` 和 `x²` 要算对。这不是配置能表达的，需要 30～80 行的 `normalizer.js`。
- **需要一个抽题策略**：如果某学科要求"一次必须出完整的一道大题及其所有小问"，
  而这和英语的"篇章级"语义一致，直接复用；若语义不同（如"同一知识点不得连续出题"）
  才写策略代码。

归一化器必须实现统一接口，注册进学科注册表：

```
// worker/src/subjects/registry.js（新增）
// 学科码 → { normalizer, picker }。找不到就回落到通用实现。
```

**约束**：归一化器只能做"等价折叠"，不能做"模糊匹配"。这是蓝本 `grade.js` 里写明的
教训——刻意没加"双写 l 简化"规则，因为它会把 `filled` 判成 `filed` 的等价形式。
新学科的归一化器同样必须遵守：**宁可判错记错，不可把错答放过**，每条规则都要有
单元测试给出它不会误判的证明。

### 4.4 新增一个学科的标准流程

改造完成后，新增学科的操作应当是这样的（这也是验收脚本要走的路径）：

1. 后台「学科管理」新建学科，填元信息 → 得到 `subject_id`
2. 准备考点表 `data/subjects/<code>/knowledge-points.json`
3. 在后台或配置文件里声明题型清单与评价标准
4. 按该学科的解析规范产出题库 JSON `data/subjects/<code>/exams/*.json`
5. 配置组卷模板（后台界面或随课程一起导入）
6. `node scripts/build-seed-sql.mjs --subject <code>` 生成种子
7. 推送 → 流水线按指纹增量导入
8. 后台校对、发布整卷
9. 管理员给相关账号授予该学科权限
10. 学员登录即可在学科选择页看到并进入

**工作量目标**：结构相似的学科，第 1～3 步与第 5 步合计不超过半天；第 4 步的题库
准备取决于资料量，不计入系统工作量。

## 5. 功能需求

### 5.1 学科管理（后台 · 新增）

**页面**：`/admin/subjects`（列表）、`/admin/subjects/:id`（详情与配置）

**列表页元素**：学科名称、学科码、状态、课程数、已发布题数、考点数、授权人数、
最近更新时间；操作为「新建」「编辑」「停用/启用」「进入配置」。

**业务规则**：

| 规则 | 说明 |
|---|---|
| 学科码唯一且不可修改 | 它会进 URL、进导出文件名、进种子文件名 |
| 学科码格式 | `^[a-z][a-z0-9-]{1,19}$`，如 `english`、`math-adv` |
| 停用学科 | 停用后学员侧不可见、不可进入；**已有数据保留不删**，管理员仍可查看与导出 |
| 删除学科 | **本期不提供删除**。学科一旦有作答数据，删除会造成报告口径断裂；只允许停用 |
| 学科下无课程 | 允许创建，但学员进入时提示"该学科尚未开放内容" |
| 配置变更的生效时点 | 评价标准变更**只对变更后产生的新作答生效**，不回溯重算历史报告；报告页标注所用标准的版本 |

**最后一条是硬要求**：评价标准可改，但改了以后老报告分数不能变。否则学员会发现
"上周考了 72 分，今天再看变成 68 分"。实现方式是 `attempts` 记录当次使用的
`rubric_version`，报告按该版本渲染。

**异常处理**：学科码重复 → 409；停用一个学员正在答题的学科 → 允许停用，但**当前进行中
的作答会话必须能正常交卷**（停用只拦新会话，不拦已开始的）。

### 5.2 学科访问权限（新增 · 本次改造的重点）

用户要求原文：「同一个账号下，不同学科有独立的访问权限，权限由管理员来设置。」

#### 5.2.1 权限模型

权限 = **全局角色** × **学科授权**，两者都满足才放行。

**全局角色**（扩展蓝本的两值枚举）：

| 角色 | 说明 | 相对蓝本 |
|---|---|---|
| `PLATFORM_ADMIN` | 平台超级管理员。管学科、管账号、管授权、管 AI 配置、看全平台数据 | 由 `SUPER_ADMIN` 改名 |
| `SUBJECT_ADMIN` | 学科管理员。只在被授权的学科内管题库、看学情 | 🆕 |
| `USER` | 学员 | 不变 |

**学科授权**（新表 `user_subject_grants`）：

| 字段 | 说明 |
|---|---|
| `user_id` + `subject_id` | 联合主键 |
| `access_level` | `STUDENT`（做题） / `MANAGER`（管题库与学情） |
| `status` | `ACTIVE` / `SUSPENDED` |
| `granted_by` / `granted_at` | 谁在什么时候授予的 |
| `expires_at` | 到期时间，可空表示长期有效 |
| `note` | 备注（如"2026 春季班"） |

**判定规则**：

```
PLATFORM_ADMIN            → 所有学科全权限，不需要授权记录
SUBJECT_ADMIN + MANAGER   → 该学科的题库管理 + 学情查看
SUBJECT_ADMIN 无授权记录  → 该学科 403
USER + STUDENT(ACTIVE 且未过期) → 该学科的学员功能
USER 无授权 / SUSPENDED / 已过期 → 该学科 403
```

#### 5.2.2 关键设计决策：学科授权不进 JWT

蓝本的 JWT 带 `role`，有效期 8 小时（`worker/src/lib/auth.js`）。

**如果把学科授权列表塞进 JWT，管理员撤销权限最长要等 8 小时才生效。** 对"权限由管理员
设置"这条需求，这是不可接受的——管理员点了撤销，界面说成功了，学员却还能继续做题。

所以：

- JWT 只带 `user_id` + 全局角色（与现状一致，不改签发逻辑）
- **学科授权每次请求查库**：一次命中主键索引的单行查询，D1 上成本可忽略
- 允许在 Worker 实例内存里缓存 ≤ 60 秒，用来削掉同一次页面加载的重复查询；
  **撤销操作必须能在 60 秒内全网生效**，这是写进验收标准的
- 读操作走缓存，**授权变更与所有写操作一律穿透到库**

#### 5.2.3 强制执行点

| 层 | 措施 |
|---|---|
| 路由 | 所有学科相关接口统一前缀 `/api/s/:subjectCode/...`，学科**从路径取，不从请求体取** |
| 中间件 | 新增 `requireSubjectAccess(level)`，挂在学科路由组上，与蓝本 `requireAuth` 同一位置 |
| 查询 | 所有学科数据查询强制带 `subject_id = ?`，**不接受前端传入的 subject_id 作为唯一依据**，必须先过中间件 |
| 越权响应 | 统一 `403 { error: 'subject_forbidden', message: '你没有该学科的访问权限，请联系管理员开通' }` |
| 学科不存在 | `404`。学科的存在性不是机密——学员需要知道平台上有哪些学科才能去申请 |

**为什么强调"从路径取"**：蓝本现有接口（如 `GET /api/assessment?courseCode=xxx`）是从
query 取课程码的，服务端只校验参数存在、不校验归属。多学科之后这条路径就是越权漏洞：
拿 A 学科的 token 传 B 学科的 code 就能读到别人的数据。改成路径参数 + 统一中间件，
是为了让"漏掉校验"变成一件做不到的事，而不是靠每个接口自觉。

#### 5.2.4 管理界面

**页面**：`/admin/users/:id/subjects`（单人视角）与 `/admin/subjects/:id/members`（单学科视角）

两个视角都要有，因为两种操作场景都真实存在：新学员入学要一次给他开好几个学科；
新学科开课要一次给一批学员开通。

**功能**：

- 单人视角：列出全部学科，每行显示当前授权状态，可直接勾选开通/关闭、设置级别与有效期
- 单学科视角：列出已授权成员，支持**批量授予**（粘贴用户名列表或多选）、批量撤销
- 每次变更写 `subject_grant_audit` 审计表：谁、什么时候、对谁、哪个学科、做了什么、原操作值
- 授权变更**不发通知**（本期无通知系统），但学员下次进入学科选择页即可看到变化

**异常处理**：给不存在的用户名授权 → 明确列出哪几个没找到，其余正常授予，不整批失败。

### 5.3 学科选择与切换（用户端 · 新增）

#### 5.3.1 学科选择页

**路由**：`/app`（登录后的默认落地页）

登录后不再直接进入"我的课程"，而是先进**学科选择页**：

- 卡片式列出该账号**有权访问且未停用**的学科
- 每张卡片显示：学科名、简介、该学科下我的进度摘要（已考次数 / 待订正错题数 / 上次活动时间）
- 无权访问的学科**不展示**（不做"灰色不可点"，避免造成"为什么不给我开"的反复询问；
  平台有哪些学科由管理员线下告知）
- 一个学科都没有 → 空状态页："管理员尚未为你开通任何学科，请联系管理员"

**降级规则**（沿用蓝本对课程选择器的处理思路）：**只有一个可访问学科时，自动进入该学科，
不显示选择页**，但顶部仍保留学科名标识。判断条件写"可访问学科数 > 1 才显示选择页"，
不硬编码学科码——这正是蓝本处理单课程时的做法，将来加学科不用回头改这一页。

#### 5.3.2 学科上下文与切换

- 进入学科后，URL 带上学科码：`/app/:subjectCode/exam/new`、`/app/:subjectCode/wrongbook` …
- 前端新增 `SubjectContext`，持有当前学科的元信息与能力包（题型、是否有写作、考点数等），
  页面据此决定渲染什么控件、显示什么文案
- 顶部导航常驻**学科切换器**（可访问学科数 > 1 时显示），切换即整体换上下文并跳回该学科首页
- 学科选择**记忆在 localStorage**，下次登录直接落到上次的学科；但**每次都要重新校验权限**，
  权限被撤销时回到选择页并提示
- **答题中不允许切换学科**。答题页（`ExamTake`/`PracticeRun`）本就不套导航外壳（蓝本设计），
  天然满足；但要防住浏览器前进后退直接改 URL 的情况——切换时若存在进行中的会话，弹确认

#### 5.3.3 URL 与旧链接

蓝本的 `/app/wrongbook` 这类路径在新平台下没有学科信息。处理：

- `/app/<非学科码路径>` → 重定向到 `/app`（学科选择页），由用户重新进入
- 不做旧链接映射：这是新部署的新系统，没有历史链接需要兼容

### 5.4 独立题库

#### 5.4.1 隔离要求

| 对象 | 隔离方式 |
|---|---|
| 真题 `exams` | 通过 `course_code` → `subject_id`，并冗余 `subject_id` 列 |
| 题组 `sections` | 新增 `subject_id` 列（蓝本没有，只能靠 `exam_id` 间接关联，报告查询要多一跳） |
| 题目 `questions` | 已有 `course_code`，新增 `subject_id` |
| 考点 `knowledge_points` | **新增 `subject_id`，主键从 `tag_id` 改为 `(subject_id, tag_id)`** |
| 解析存疑记录 `exam_parsing_notes` | 随 `exam_id` 隔离，查询时带学科过滤 |
| 组卷模板 `exam_templates` | 已按 `course_code` 隔离，课程归学科 |

**考点是重点**：蓝本的 `knowledge_points.name` 有 `UNIQUE` 约束，全局唯一。英语的
"固定搭配"和语文的"固定搭配"含义不同却会撞名。改造后 `UNIQUE` 降为
`(subject_id, name)` 联合唯一。

**跨学科抽题是禁止的**：组卷、练习、错题本的所有查询必须带 `subject_id`，
绝不允许出现"抽到别的学科的题"。这一条要写成测试断言。

#### 5.4.2 题库管线按学科分目录

```
data/
  subjects/
    english/
      knowledge-points.json
      PARSING_GUIDE.md          ← 该学科的解析规范
      exams/13000-2024-04.json
    math-adv/
      knowledge-points.json
      PARSING_GUIDE.md
      exams/00023-2025-04.json
```

`scripts/build-seed-sql.mjs` 增加 `--subject` 参数，按学科生成种子；
**种子指纹机制（`seed_state`）原样保留**——它是蓝本为了不烧 D1 写入额度专门做的，
多学科之后只会更重要（§11.3）。

#### 5.4.3 题型开放

蓝本 `questions.question_type` 的 `CHECK` 约束只认三种题型。改造后：

- 去掉 `CHECK`，改为外键引用 `subject_question_types(subject_id, type_code)`
- 平台预置一组通用题型，学科从中挑选并可自定义：

| 题型码 | 名称 | 客观 | 默认进练习 | 判分方式 |
|---|---|---|---|---|
| `single_choice` | 单选 | ✅ | ✅ | 选项字母精确匹配 |
| `multi_choice` | 多选 | ✅ | ✅ | 选项集合完全一致（是否给部分分由学科配置） |
| `true_false` | 判断 | ✅ | ✅ | 精确匹配 |
| `fill_text` | 文本填空 | ✅ | ✅ | 归一化后精确匹配（英语的完形填空即此类） |
| `fill_numeric` | 数值填空 | ✅ | ✅ | 数值容差比较，容差由学科配置 |
| `short_answer` | 简答 | ❌ | 由学科配置 | AI 按 rubric 评分 |
| `essay` | 写作/论述 | ❌ | 默认不进练习 | AI 按 rubric 评分 |
| `calculation` | 计算/解答 | ❌ | 由学科配置 | AI 按步骤 rubric 评分 |

英语学科迁入时只启用 `single_choice`、`fill_text`（对应蓝本的
`fill_blank_transform`）、`essay` 三种，行为与现状一致。

### 5.5 独立例题解析

用户要求"独立的例题解析"。拆成两件相关但不同的事，两件都要做：

#### 5.5.1 题目解析（Explanation）：每道题的结构化解题说明

**现状**：蓝本只有 `questions.answer_explanation` 一个自由文本字段（原卷官方解析），
外加 AI 事后生成的 `wrong_items.error_analysis` / `memory_point` 两个字段。
**没有结构，没有来源标记，没有审核状态，没有版本。**

**改造**：新增 `question_explanations` 表，一道题可以有多条解析：

| 字段 | 说明 |
|---|---|
| `subject_id` / `question_id` | 归属 |
| `kind` | `OFFICIAL`（原卷官方解析） / `MANUAL`（人工撰写） / `AI`（AI 生成） |
| `content` | JSON，**结构由该学科的 `subject_explanation_schema` 定义** |
| `source_model` | AI 生成时记录模型与时间，便于追溯质量问题 |
| `review_status` | `待审` / `已发布` / `已打回` |
| `reviewed_by` / `reviewed_at` | 审核人 |
| `version` | 同一 kind 的历史版本保留，展示取最新已发布 |

**解析结构按学科定义**，例如：

| 学科 | 解析字段 |
|---|---|
| 英语 | 定位依据、词义辨析、句子结构、干扰项为什么错 |
| 数学 | 解题步骤（有序数组）、用到的公式/定理、关键变形、易错点、同类题提示 |
| 政治/法律 | 考点出处、采分点清单、关键词、常见混淆点 |

**展示优先级**：已发布的 `MANUAL` > `OFFICIAL` > 已发布的 `AI`。
学员侧**必须标明解析来源**："本解析由 AI 生成，仅供参考"——这是蓝本
`docs/项目全档.md` §9.3 那个教训的延伸：AI 产出的东西不能让学员误以为是权威答案。

**AI 生成解析**沿用蓝本的分层原则（PRD §10.3）：主链路不依赖 AI，解析生成是异步补充，
失败不影响做题与判分。

#### 5.5.2 例题（Exemplar）：学科自建的教学用典型题

**这是新增的内容实体**，与真题题库分开：

- 不来自真题，由学科管理员录入，用于"讲"而不是"考"
- **不进入组卷与练习抽题池**（硬约束，写成测试断言）
- 含：题面、完整解题过程、涉及考点、难度、适用场景说明
- 挂在考点上：学员在错题本或能力评估里看到某个薄弱考点时，可以跳去看该考点的例题
- 页面：学员端 `/app/:subjectCode/exemplars`，后台 `/admin/subjects/:id/exemplars`

**为什么单列**：真题解析回答"这道题为什么选 B"；例题回答"这类题该怎么想"。
把后者硬塞进真题解析，会让解析变得又长又不聚焦。

### 5.6 独立评价标准

"评价标准"覆盖五件事，全部按学科配置，存入 `subject_rubrics`（JSON + 版本号）：

#### ① 客观题判分规则

| 参数 | 说明 | 英语取值（保持现状） |
|---|---|---|
| `normalizer` | 归一化器标识 | `english`（英美拼写对照表 + 三条后缀规则） |
| `case_sensitive` | 是否区分大小写 | `false` |
| `numeric_tolerance` | 数值题绝对/相对容差 | 不适用 |
| `partial_credit` | 多选是否给部分分 | 不适用 |
| `blank_is_zero` | 未作答记 0 分 | `true` |

**不变的骨架**：只有满分或零分、不做模糊匹配、规则判不对的一律记错 —— 这是蓝本
`grade.js` 的核心立场，跨学科同样成立，不允许学科配置推翻。

#### ② 主观题评分维度与权重

现状是写死在 `tutor.js` 里的五个英语作文维度。改造为配置：

```
rubric.subjective.<question_type> = {
  dimensions: [ { key, name, max, weight, guide } ... ],
  total_score: 30,
  scale: 6           // 每个维度的打分区间上限
}
```

英语作文迁入时填现有值：content 0.30 / language 0.25 / vocabulary 0.15 /
coherence 0.20 / length 0.10，`scale=6`，`total_score=30`。**迁入后由测试断言
新旧算法在同一组输入下得分完全一致**，证明配置化没有改变行为。

**保留蓝本的关键约束**：维度分一个都读不到时必须抛 `ai_bad_shape`，
**绝不静默回落 0 分**。真的 0 分和读不到 0 分必须分得开。这条是线上踩出来的，
配置化不能把它弄丢。

#### ③ 掌握度分档阈值

现状写死在 `mastery.js`：

```
未测     做过 0 题
薄弱     最近一次答错，或整体正确率 < 50%
待巩固   做对过但还不够稳
已掌握   做过 ≥3 题 且 连对 ≥3 次
```

改造为 `rubric.mastery = { min_questions: 3, min_streak: 3, weak_accuracy: 0.5 }`。

#### ④ 自适应抽题权重

现状 `tagWeight()` 写死 2.0 / 5.0 / 2.0 / 1.0 / 0.3。改造为配置表。
**"连对三次也不归零（保底 0.3）"的设计意图必须在配置里写明注释**——它是为了复验
"蒙对"的考点，学科改这个值时要知道自己在改什么。

#### ⑤ 能力评估参数

| 参数 | 现状 | 改造 |
|---|---|---|
| 时间衰减权重 | `[0.35, 0.25, 0.20, 0.12, 0.08]` 写死 | 按学科配置 |
| 最少样本数 | 2 次模考 | 按学科配置 |
| 预测区间宽度 | `max(3, 历史标准差)` | 按学科配置下限 |
| 满分 | 100 写死在裁剪逻辑里 | 取课程满分 |
| 及格线 | 无 | 🆕 按学科配置，报告里显示"距及格还差 X 分" |

**双层结构不变**：统计层与 AI 层并列呈现、互不覆盖。

#### ⑥ 错题订正阈值

现状 `CORRECT_STREAK_TO_CLEAR = 2`。改为按学科配置，默认 2。

### 5.8 报告的学科分层

用户要求："所有的报告需要根据不同学科的区分。"逐张报告落实：

| 报告 | 页面 | 改造 |
|---|---|---|
| 模考成绩报告 | `ExamReport` | 数据本就按 `attempt_id` 取，天然隔离；**报告头部显示学科名 + 评价标准版本** |
| 练习总结 | `PracticeSummary` | 同上 |
| 错题本 | `WrongBook` | 查询加 `subject_id`；筛选器的考点列表按学科取 |
| 能力评估 | `Assessment` | 查询加 `subject_id`；**能力评估按学科独立计算，不跨学科合并** |
| 历史记录 | `History` | 默认只看当前学科；提供"查看全部学科"开关 |
| 学员学情（后台） | `admin/Students` | ⚠️ **当前 SQL 完全没有课程过滤**，多学科后统计会把所有学科混在一起。必须加学科筛选器，默认按学科查看 |
| 题库总览（后台） | `admin/Dashboard` | 同上，必须加学科维度 |
| 数据导出（后台） | `admin/Export` | 导出参数加 `subjectCode`；导出文件名带学科码；JSON 内含学科元信息 |

**需要点名的现状缺陷**：`worker/src/routes/admin-stats.js` 的 `/students` 与
`/overview` 两个查询**没有任何课程/学科过滤**，是全库聚合。单学科时这不算错，
多学科之后它会直接产出错误数据（学员英语考了 5 次、数学考了 3 次，看板会显示"考了
8 次、平均分是两个学科混算的平均"）。这不是新增需求，是**必须修的既有缺陷**。

**统一要求**：任何一张报告页面，都必须在显眼处标明"这是哪个学科的数据"。
跨学科平台最容易出的事故是学员/管理员看错学科还浑然不觉。

### 5.9 跨学科视图（增值）

既然是跨学科平台，只做隔离是不够的，还要有只有跨学科才能给出的东西。**本期只做
数据汇总层，不做分析算法**（§1.4）：

**学员端** `/app/overview`（学科选择页下方或独立页）：

- 各学科的学习时长、作答题数、平均分、待订正错题数横向对比
- 学习活跃度日历（不分学科，看整体投入）
- 各学科的能力评估预测分并列（**不做加权总分**——不同学科满分与难度不可比，
  合成一个总分是误导）

**后台** `/admin/overview`：

- 各学科的学员数、活跃数、题库规模、作答量、AI 用量对比
- 学科健康度：题库是否够组卷、存疑题占比、AI 失败率
- 仅 `PLATFORM_ADMIN` 可见；`SUBJECT_ADMIN` 只能看自己被授权的学科

| `GET /api/wrongbook` | `GET /api/s/:subjectCode/wrongbook` | 同上 |
| `GET /api/admin/stats/students` | `GET /api/admin/s/:subjectCode/stats/students` | **加学科过滤（修既有缺陷）** |
| `GET /api/admin/stats/overview` | 拆成学科级 + `GET /api/admin/overview` 跨学科级 | 同上 |
| `GET /api/admin/stats/export/*` | `GET /api/admin/s/:subjectCode/export/*` | 导出按学科 |
| 其余 | 路径加前缀，逻辑不变 | |

**保持蓝本的一条铁律**：鉴权中间件按前缀挂，**绝不挂在 `/api/*` 上**——那样会把
`/api/health` 和 `/api/auth/login` 也挡住。新增的 `requireSubjectAccess` 同样只挂在
`/api/s/*` 与 `/api/admin/s/*` 上。

**错误码新增**：

| 码 | HTTP | 场景 |
|---|---|---|
| `subject_not_found` | 404 | 学科码不存在 |
| `subject_forbidden` | 403 | 无该学科访问权限 |
| `subject_suspended` | 403 | 学科已停用 |
| `grant_expired` | 403 | 授权已过期 |
| `subject_not_ready` | 422 | 学科下没有可用题库/模板 |

蓝本已有的 `storage_quota_exceeded`（503）与 `insufficient_questions`（422）保留。

### 10.4 部署流水线

沿用蓝本 `deploy-worker.yml` 的步骤结构与**步骤顺序**——顺序本身是踩坑改出来的：
部署必须排在数据装载之前，否则导入一失败后面的部署整步跳过，修复代码永远上不了线。

（该工作流实测有 20 个命名步骤，蓝本 `docs/项目全档.md` §8.2 记作"22 步"，以工作流
文件为准；改造时顺手把蓝本文档这处数字改对。）

新增步骤：

```
… → 执行迁移 → 部署 Worker → 写入密钥
  → 🆕 创建默认学科（english）
  → 🆕 按学科逐个导入题库（指纹跳过 + 每个学科单独一步，便于定位失败）
  → 放行题库 → 等待响应 → 初始化平台管理员
  → 🆕 初始化学科授权（给种子账号开通 english）
  → 取管理员令牌 → 配置 AI → 线上验证 → 输出汇总
```

**线上验证必须保留蓝本的"写入哨兵"断言**（`写入已恢复（AI 配置 N 秒前刚落库）`）：
D1 写配额耗尽时所有读接口都正常、只有写会失败，十几条读类断言全绿说明不了站点能用。

**新增两条验证断言**：

- 跨学科越权：用只授权了 A 学科的探针账号访问 B 学科，必须 403
- 学科隔离：A 学科的组卷结果里不得出现任何 B 学科的题目

## 11. 非功能需求

### 11.1 性能

沿用蓝本 PRD §11 的指标，并对新增路径提出要求：

| 项 | 要求 |
|---|---|
| 页面首屏 | < 2s |
| 学科选择页 | < 1s（它是登录后的第一屏，慢会被直接感知） |
| 学科权限校验 | < 20ms（单行索引查询；缓存命中时 0） |
| 组卷接口 | < 3s |
| 练习出题接口 | < 1s |
| AI 类接口 | < 30s，且有加载态 |
| 学科切换 | < 500ms（只换上下文，不重载整个应用） |

### 11.2 安全

| 项 | 要求 |
|---|---|
| 密码 | bcrypt 加盐哈希 |
| JWT | 8 小时过期，只带 `user_id` 与全局角色 |
| 登录限流 | 连续 5 次失败锁 10 分钟 |
| API Key | 服务端 AES-GCM 加密存储，读出一律脱敏（`sk-****3456`），明文绝不下发前端 |
| 用户数据隔离 | 强制按 `userId` 过滤，不接受前端传入 |
| **学科数据隔离** | 🆕 强制按中间件解析的 `subject_id` 过滤，不接受请求体传入 |
| **权限撤销时效** | 🆕 ≤ 60 秒全网生效 |
| **越权审计** | 🆕 所有 `subject_forbidden` 响应记日志，便于发现探测行为 |
| 仓库公开时 | 凭据只进 GitHub Secrets 与 Worker Secrets |

### 11.3 容量与配额（多学科后的新约束）

**这是多学科带来的最实际的风险。**

D1 免费档每天 10 万行写入，世界时零点（北京时间早八点）重置。蓝本实测：
**一个学科 20 套真题的完整重导约 5700 行写入。**

推算：

| 学科数 | 首次全量导入写入量 | 是否撞上限 |
|---|---|---|
| 1 | ~5,700 | 否 |
| 5 | ~28,500 | 否 |
| 10 | ~57,000 | 否，但余量不多 |
| 17 | ~96,900 | **逼近上限** |
| 20+ | > 10 万 | **必然失败** |

**要求**：

1. **种子指纹机制（`seed_state`）必须原样保留并按学科分文件**，稳态部署写入量为 0
2. 导入按学科**分步执行**，每个学科单独一步 —— 一个学科失败不拖垮其他学科，
   且日志里能直接看出是哪个学科失败
3. 导入前**预估并打印行数**，接近额度时主动中止并提示"明日继续"，
   而不是撞上去半途失败留下脏数据
4. **内容指纹必须与数据同批入库**（蓝本踩过的坑：分两步写，数据进去了指纹没记上，
   下次重导再死在同一处，每跑一次白烧几百行，永远走不出来）
5. 配额耗尽时的降级方向是"写不进"而不是"打不开"：登录、查看已有记录照常；
   组卷、交卷、练习作答返回 503 并说明恢复时间

**如果学科数确定会超过 10 个，需要在立项时就评估 D1 付费档或换库**，这是产品决策，
列入 §15。

### 11.4 可扩展性

| 项 | 要求 |
|---|---|
| 新增结构相似的学科 | **零代码**（§1.5 成功判据） |
| 新增需要新判分语义的学科 | 新增 1 个归一化器文件 + 其单元测试，不改任何既有学科的代码 |
| 新增题型 | 在 `subject_question_types` 里声明 + 前端注册一个控件，不改判分骨架 |
| 修改评价标准 | 纯配置，不改代码，且不影响历史报告 |

### 11.5 兼容性与可用性

- Chrome / Edge / Safari 最新两个大版本
- 响应式：手机 / 平板 / PC 三种宽度
- 依托 Cloudflare 全球网络，无休眠；D1 数据持久

### 11.6 测试

沿用蓝本的四层测试策略（240 条断言）并扩充：

| 层 | 新增内容 |
|---|---|
| 单元测试 | 每个学科归一化器的等价与**非等价**用例（证明不会误判） |
| 冒烟测试 | 每层都要有"两个学科并存"的场景，不能只测单学科 |

## 附录 A：蓝本关键设计的保留清单

改造过程中**不允许被改掉**的蓝本设计决策，每一条背后都有踩过的坑：

| # | 设计 | 出处 |
|---|---|---|
| 1 | 鉴权中间件按前缀挂，绝不挂 `/api/*` | 挂了会挡住健康检查与登录 |
| 2 | `run_worker_first = ["/api/*"]` | 少了这行未知接口返回 HTML，前端拿去 `JSON.parse` |
| 3 | AI 调用强制 `enable_thinking: false` | 推理模型不关思考会把 token 花光返回空对象，延迟从 3s 涨到 15s+ |
| 4 | AI 只增强体验，主链路不依赖 AI | 交卷先出客观题成绩，AI 事后补 |
| 5 | AI 返回读不到维度分必须报错，不静默回落 0 | 线上出过"理直气壮的零分" |
| 6 | AI 错题分析并发上限 5 | 串行会让请求 80 秒以上超时；替身测不出来 |
| 7 | 错题在判分时落库，不等 AI | AI 不可用时错题本照常能用 |
| 8 | 配额耗尽的降级方向是"写不进"不是"打不开" | 记账写入失败不该把人挡在登录外 |
| 9 | 内容指纹与数据同批入库 | 分两步写会导致永远走不出重导循环 |
| 10 | 部署步骤排在数据装载之前 | 导入失败会让修复代码永远上不了线 |
| 11 | 判分不做模糊匹配，宁可判错记错 | "双写 l 简化"会把 `filled` 判成 `filed` |
| 12 | 抽题权重连对三次也不归零 | 要复验"蒙对"的考点 |
| 13 | 组卷凑不满返回 422，不出残缺卷子 | |
| 14 | 每套测试占独立端口 | 撞过一次，症状是随机的、与改动无关的失败 |
| 15 | 跑测试必须检查"小结"是否存在 | 脚本可能提前退出，"没有 FAIL"不等于通过 |
| 16 | AI 替身不用来证明功能可用 | 它对时延和返回结构结构性失明 |
| 17 | 线上验证必须有写入哨兵 | 读接口全绿说明不了站点能用 |
| 18 | 条形图用 HTML 不用 SVG | SVG 字号随 viewBox 缩放，手机上 12px 只剩 7.7px |
| 19 | 练习已答计数从服务端取 | 只存前端状态时刷新会归零 |
| 20 | 单一选项时不显示选择器，但判断写"数量 > 1" | 将来加第二个不用回头改页面 |

**第 20 条特别值得注意**：蓝本处理"只有一门课程"时就是这么写的，本次学科选择页
沿用同样的思路（§5.3.1）。这说明蓝本作者已经预见到了扩展的可能——本次改造是把这个
预留真正用起来。
