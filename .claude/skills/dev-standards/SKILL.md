# 开发标准

这份标准针对一类特定的失败：**它不会报错。** 测试是绿的、接口返回 200、健康检查
全过，但结果是错的。这类问题在本地几乎发现不了，往往要到线上、要到用户手里才暴露，
而那时排查成本已经翻了很多倍。

下面按使用场景组织。每条给的是**可以当场执行的动作**，不是原则。展开的理由、失效
模式和更多检验方法在 `references/开发标准.md`（29 条完整版）——某条你觉得不确定
要不要遵守时去查它，那里写了不遵守会以什么形式出事。

---

## 写测试和断言时

**每写完一条断言，先证明它能失败。** 把被测逻辑临时改成返回常量或直接删掉，跑一次，
确认变红，然后改回。红不了的断言是装饰品：它会一直绿，直到某天有人发现功能其实早
就坏了。

**期望值和被测值不能同源。** 用被测系统自己的输出去校验它自己，写出来的是恒等式。
典型形态是"拿数据库里的 X 去对接口返回的 X"——两边同一个来源，永远相等。
自检：问"这两个数如果不相等，可能是什么原因造成的"，想不出任何原因就说明同源了。

**会随业务规则变的数字不要写死。** 从数据现算。写死的常量在规则调整后会一批同时
误报，而它们其实指向同一个改动，排查成本被放大好几倍。

**挑测试样本时，先确认它在被测流程里真的可达，并把决定可达性的那个属性打印出来。**
挑了一个流程根本走不到的样本，测出来的是数据规模、排序策略或搜索深度，不是你想验
的那条规则。**按 id、字母序、插入顺序取"第一条"是这个错误的高发写法**——排在第一
不等于满足被测条件。

举例：要验证"连续答对两次就标记已订正"，如果挑的那道题所属分类下有几十道题，而出题
按"做过次数"升序排，有限轮次根本轮不到它。该挑的是**所属分类里题目最少**的那道。

**只断言被测逻辑承诺过的性质。** 把自己的直觉当规格，会写出在某些合法输入下必然红
的断言，然后团队开始把它当"抖动"忽略。写之前先能用一句话说清被测逻辑保证了什么。

**失败输出要能区分"逻辑错"和"数据不够"。** 只有"期望 X 实际 Y"是不够的，把选中
对象的关键属性一起打印，否则每次红都要重新加日志再跑一遍。

## 接外部服务、写或用替身时

**替身能证明协议约束和降级路径，不能证明"功能可用"。** 替身是你按期望写的，所以
它对两类问题结构性失明，而且这两类出事时都不报错，表现为"成功但结果不对"：

- **时延**：串行调用在替身下是零成本。接上真实依赖后，单次延迟 × 循环次数可能超过
  任何客户端超时。服务端还在干活，调用方已经断开，两边都"没错"。
- **返回结构**：真实服务返回的数据合法但形状不同（键名不一样、数字变成字符串、多包
  了一层），解析全部落空。如果解析失败时又回落了默认值，就会得到一个理直气壮的错误
  结果。

**所以：发布前对真实服务跑一次端到端，并把这次运行固化成可重复执行的流水线。**
问自己"这条链路最近一次真实调用是什么时候"，答不上来就等于没验过。

**对同一个慢依赖的 N 次调用，默认写成有并发上限的并行，不要串行循环。** 判据：单次
耗时 × 最大次数，超过 30 秒就必须改。并发上限要同时考虑总时长和对方的速率限制。

## 写错误处理时

**读不到值就抛错，不要回落默认值。** 默认值往往是 0 / 空 / false，恰好又是合法结果，
于是"我没读懂"被伪装成"结果就是这样"，没有任何人知道。
自检：问"真实的默认值和读取失败，在输出上分得开吗"。分不开就必须抛错。

**分清两类失败，它们的处理方向相反：**

| 类型 | 例子 | 怎么办 |
|---|---|---|
| 不知道答案 | 核心计算失败、外部数据读不懂 | 抛错，让上层看见 |
| 答案有了，只是没记上账 | 审计日志、最后登录时间、统计计数写失败 | 吞掉并告警，不拖垮主流程 |

判据是一句话：**这次失败改变了用户要的那个结果吗。** 没改变就降级，改变了就抛错。
两个方向搞反都会出事——前者当后者，用户拿到错误结果；后者当前者，一次无关紧要的
写入失败让主功能不可用。

**解析类错误信息里要带上你实际收到的内容特征**（顶层键名、类型、长度、前若干字符）。
这类问题往往只在真实环境出现，复现成本极高，错误信息不含证据就只能靠猜。

## 改代码时

**文本锚点取完整语法单元（整行、整个语句），不要取会出现在更大结构中间的片段。**
锚点匹配到某行后半截时，插入的内容会把这行劈成两半，前半截的修饰符跑去修饰新内容——
改动看起来成功了，语义完全变样。替换后把改动处上下三行读一遍。

**静态检查通过不等于能跑。** `node --check`、`bash -n`、编译器、类型检查都查不出
导出丢失、引用错对象、分支永不进入这类问题。改完必须真正执行一次改动路径。

---

## 准备提交或发布时

**跑全套回归，不只跑改动那套。** 某次规则调整可能让另一个模块的断言早已失效，而那
套测试此后再没跑过。问自己：距离上次跑全套过了多久，期间改过几处规则。

**汇总输出要能区分"通过"和"根本没跑到结论"。** 脚本可能在准备阶段就退出，没有任何
失败输出，于是"没有 FAIL"被误读成"通过"。缺少结论本身就要当作失败，例如：

```bash
for s in suite-a suite-b suite-c; do
  echo "=== $s ==="
  run_suite "$s" 2>&1 | grep -E "FAIL|小结" || echo "  !! 没有结论，视为失败"
done
```

**照着自查清单过一遍**（完整版在 `references/开发标准.md` 末尾）：

```
□ 每条断言，被测逻辑删掉后会红
□ 期望值与被测值不同源，没有写死的魔数
□ 选中的样本在被测流程里可达，关键属性已打印
□ 真实依赖跑过一次端到端，不是只跑了替身
□ 单次耗时 × 最大次数 在可接受范围内
□ 没有静默兜底；记账类失败不拖垮主流程
□ 解析错误带上了实际看到的内容特征
□ 真的运行过一次，不只是静态检查通过
□ 跑了全套回归，汇总能区分"通过"和"没跑到结论"
□ 说清了哪些验证过、哪些没有
```

## 涉及配额、幂等、流水线顺序时

去读 `references/开发标准.md` 第五章。要点：

- **"已完成"的标记必须和被标记的操作原子落地。** 操作成功、标记失败，系统认为没做过，
  下次重做又在同一处失败——形成消耗配额但永不推进的死循环，而且越试越糟。
- **代码发布排在数据装载之前。** 数据侧因配额失败时，后续发布步骤会整步跳过，累积
  多次的代码变更一行都没上线——其中可能正好包含修复问题的那个。
- **配额耗尽的降级方向是"写不进"，不是"打不开"。** 读路径和登录必须继续可用。

## 涉及健康检查、监控、降级时

去读 `references/开发标准.md` 第六章。要点：

- **全绿不等于可用。** 如果某类故障只影响一部分操作（比如只影响写），检查里必须有
  专门覆盖那一部分的项，否则十几条读类断言全绿也说明不了系统能用。
- **给某条路径加降级之前，先确认它是不是正被当作健康探针。** 是的话要同时补一个新
  探针，否则系统会从"看得见的坏"变成"看不见的坏"。

## 在陌生或受限环境里工作时

去读 `references/开发标准.md` 第七章。要点：动手前先确认网络出站策略和可用工具；
碰到限制照实报告，不要绕过 TLS 校验或代理；某个验证手段不可用时，明确说明你换了
什么方式验证、**哪一部分没有验证过**。

---

## 交付时

**说清验证边界。** 明确区分"验证过的"和"没验证的"，测试失败要带上原始输出，跳过的
步骤要说明。别让接收方基于错误的完成度做后续决策。

**写用户文档前，先从运行中的系统或源码里把实际文案和行为抓出来**，按实际的写，不要
照着设计文档编——那样写出来的文档与用户看到的对不上。这个过程还会顺带发现界面上残留
的过期文案。
